# Лабораторная работа № 4.1

## Тема: Транзакции и выполнение запросов в PostgreSQL

---

## 1. Краткие теоретические сведения

### 1.1. Клиент и сервер

PostgreSQL работает по модели «клиент-сервер». Клиент (psql, приложение) подключается к серверу по протоколу и общается с ним: отправляет SQL-запросы, получает результаты, управляет транзакциями. Сервер выполняет аутентификацию при подключении к базе данных кластера.

### 1.2. Транзакции и автофиксация

Транзакция — последовательность операций, выполняемая как единое целое. Свойства ACID:
- **Атомарность** — всё или ничего.
- **Согласованность** — переход между согласованными состояниями.
- **Изоляция** — параллельные транзакции не влияют друг на друга.
- **Долговечность** — после фиксации данные не теряются.

По умолчанию psql работает в режиме **автофиксации** (`AUTOCOMMIT = on`): каждая команда сразу фиксируется. Явное управление:
```sql
BEGIN;               -- начать транзакцию
COMMIT;              -- зафиксировать
ROLLBACK;            -- отменить
SAVEPOINT имя;       -- точка сохранения
ROLLBACK TO имя;     -- откат к точке сохранения
```

### 1.3. Выполнение запроса

Запрос проходит четыре стадии:
1. **Разбор** — синтаксический и семантический (проверка объектов по системному каталогу).
2. **Переписывание** — применение правил (например, подстановка текста представления).
3. **Планирование** — построение плана на основе статистики. Планировщик решает, использовать ли индекс, какой метод соединения выбрать и т.д.
4. **Выполнение** — выполнение плана и возврат результата.

Для анализа используется `EXPLAIN` (план без выполнения) и `EXPLAIN ANALYZE` (план с фактическим выполнением).

> **Примечание про индексы.** Индекс — это дополнительная структура данных (обычно B-дерево), которая ускоряет поиск строк по значению столбца. Однако индексы:
> - **замедляют** операции вставки, обновления и удаления (индекс нужно поддерживать в актуальном состоянии);
> - **занимают дополнительное место** на диске;
> - **не всегда используются** планировщиком. Если запрос выбирает большую часть таблицы (например, более 10–20% строк), последовательное сканирование (`Seq Scan`) может оказаться быстрее, чем чтение через индекс (`Index Scan`), так как при индексном доступе требуется дополнительно читать страницы таблицы.
>
> Поэтому индексы создают целенаправленно — под конкретные запросы, а не «на всякий случай».

### 1.4. Подготовленные операторы

Если один и тот же запрос выполняется многократно, разбор и планирование можно выполнить один раз — это делает подготовленный оператор. Дополнительное преимущество — **защита от SQL-инъекций**, так как параметры передаются отдельно от текста запроса.

```sql
PREPARE имя(типы) AS запрос;
EXECUTE имя(значения);
DEALLOCATE имя;
```

Список подготовленных операторов в текущем сеансе — в представлении `pg_prepared_statements`.

### 1.5. Курсоры

Курсор позволяет получать результат **построчно**, а не сразу целиком. Это удобно для больших выборок: данные читаются порциями по мере необходимости.

```sql
BEGIN;
DECLARE имя CURSOR FOR запрос;
FETCH имя;         -- одна строка
FETCH 10 имя;      -- 10 строк
FETCH ALL имя;     -- все оставшиеся
CLOSE имя;
COMMIT;
```

**Цель:** освоить подключение к PostgreSQL и познакомиться с информацией о соединении.

**Ожидаемый результат:** вы умеете подключаться к серверу и получать базовую информацию о соединении.

### Задание 2. Транзакции и автофиксация

**Цель:** изучить режим автофиксации, явное управление транзакциями и точки сохранения.

**Техническое задание:**

1. В **Сеансе 1** создайте таблицу и вставьте строку (без явного `BEGIN` — сработает автофиксация):
   ```sql
   CREATE TABLE tx (id integer, val text);
   INSERT INTO tx VALUES (1, 'autocommit');
   ```
2. В **Сеансе 2** выполните:
   ```sql
   SELECT * FROM tx;
   ```
   **Вопрос:** видна ли строка? Почему?
3. В **Сеансе 1** отключите автофиксацию:
   ```sql
   \set AUTOCOMMIT off
   ```
4. Вставьте ещё одну строку:
   ```sql
   INSERT INTO tx VALUES (2, 'no autocommit');
   ```
5. В **Сеансе 2** снова выполните `SELECT * FROM tx;`. Сколько строк видно? Почему?
6. В **Сеансе 1** зафиксируйте изменения:
   ```sql
   COMMIT;
   ```
7. В **Сеансе 2** проверьте снова. Что изменилось?
8. Верните автофиксацию в **Сеансе 1**:
   ```sql
   \set AUTOCOMMIT on
   ```
9. Продемонстрируйте работу `SAVEPOINT` в **Сеансе 1**:
   ```sql
   BEGIN;
   INSERT INTO tx VALUES (3, 'before savepoint');
   SAVEPOINT sp1;
   INSERT INTO tx VALUES (4, 'after savepoint');
   SELECT * FROM tx;
   ROLLBACK TO sp1;
   SELECT * FROM tx;   -- строка 4 исчезла, строка 3 осталась
   COMMIT;
   ```

**Ожидаемый результат:** при автофиксации изменения видны сразу; без неё — только после `COMMIT`. `ROLLBACK TO SAVEPOINT` отменяет часть транзакции, не прерывая её целиком.

**Вопрос для самопроверки:** чем отличается `ROLLBACK` от `ROLLBACK TO SAVEPOINT`?

### Задание 3. Этапы выполнения запроса и `EXPLAIN`

**Цель:** научиться читать план запроса и понимать, как планировщик выбирает метод доступа.

**Техническое задание:**

1. В **Сеансе 1** создайте таблицу и заполните её:
   ```sql
   CREATE TABLE explain_test (id serial PRIMARY KEY, name text);
   INSERT INTO explain_test (name)
   SELECT 'name_' || g FROM generate_series(1, 10000) g;
   ANALYZE explain_test;
   ```
2. Посмотрите план запроса по первичному ключу (без выполнения):
   ```sql
   EXPLAIN SELECT * FROM explain_test WHERE id = 500;
   ```
   Запишите метод доступа. Почему выбран именно он?
3. Выполните с фактическим выполнением:
   ```sql
   EXPLAIN ANALYZE SELECT * FROM explain_test WHERE id = 500;
   ```
   Сравните оценку (`rows`) с фактическим числом строк и посмотрите на `actual time`.
4. Выполните запрос по полю без индекса:
   ```sql
   EXPLAIN ANALYZE SELECT * FROM explain_test WHERE name = 'name_500';
   ```
   Какой метод доступа теперь? Почему?
5. Создайте индекс по полю `name` и повторите:
   ```sql
   CREATE INDEX explain_test_name_idx ON explain_test(name);
   ANALYZE explain_test;
   EXPLAIN ANALYZE SELECT * FROM explain_test WHERE name = 'name_500';
   ```
   Сравните план до и после создания индекса.
6. Продемонстрируйте этап **переписывания**: создайте представление и посмотрите план запроса к нему:
   ```sql
   CREATE VIEW v_explain AS SELECT * FROM explain_test WHERE id < 100;
   EXPLAIN SELECT * FROM v_explain WHERE name = 'name_50';
   ```
   Обратите внимание: в плане нет узла «view» — представление «растворяется» в базовом запросе.
7. **Проверьте, когда индекс не используется.** Выполните запрос, выбирающий большую часть таблицы:
   ```sql
   EXPLAIN ANALYZE SELECT * FROM explain_test WHERE id > 100;
   ```
   Несмотря на наличие первичного ключа, планировщик, скорее всего, выберет `Seq Scan`. Почему? Сравните с запросом `WHERE id = 500`.

> **Примечание про индексы (дополнение к шагу 5).**
> - Индекс ускоряет **поиск** конкретных значений, но **замедляет** вставку, обновление и удаление (индекс нужно поддерживать).
> - Индекс **занимает место** на диске (иногда больше, чем сама таблица).
> - Планировщик использует индекс только тогда, когда это выгодно: если запрос выбирает небольшую долю строк. При выборке большой части таблицы последовательное сканирование (`Seq Scan`) обычно быстрее, так как не требует дополнительных обращений к индексным страницам.
> - Индексы создают **под конкретные запросы**, а не «на всякий случай».

**Ожидаемый результат:** вы видите, как планировщик выбирает метод доступа в зависимости от индексов и статистики, и как представления переписываются в базовый запрос.

**Вопрос для самопроверки:** зачем нужна команда `ANALYZE` перед анализом плана?

### Задание 4. Подготовленные операторы и оценка ускорения

**Цель:** освоить `PREPARE`/`EXECUTE` и экспериментально проверить, даёт ли подготовка выигрыш в скорости.

#### Часть A. Работа с подготовленными операторами

1. В **Сеансе 1** подготовьте оператор:
   ```sql
   PREPARE get_user(integer) AS
   SELECT * FROM explain_test WHERE id = $1;
   ```
2. Выполните его с разными параметрами:
   ```sql
   EXECUTE get_user(100);
   EXECUTE get_user(200);
   ```
3. Посмотрите список подготовленных операторов:
   ```sql
   SELECT name, statement, parameter_types, generic_plans, custom_plans
   FROM pg_prepared_statements;
   ```
   Обратите внимание на поля `generic_plans` и `custom_plans` — сколько раз использовался обобщённый и специализированный план.
4. Посмотрите план подготовленного оператора:
   ```sql
   EXPLAIN EXECUTE get_user(100);
   ```
5. Удалите оператор:
   ```sql
   DEALLOCATE get_user;
   ```

#### Часть B. Сравнение производительности: без подготовки vs с подготовкой

**Идея:** выполнить один и тот же запрос 1000 раз двумя способами — «в лоб» (каждый раз заново разбирается и планируется) и через `PREPARE`/`EXECUTE` — и сравнить суммарное время. Используем **сложный** запрос с соединением и агрегацией, чтобы разница была заметнее.

**Шаг 1. Подготовьте данные**

```sql
CREATE TABLE users (
  id serial PRIMARY KEY,
  name text
);

CREATE TABLE orders (
  id serial PRIMARY KEY,
  user_id integer,
  amount numeric
);

INSERT INTO users (name)
SELECT 'user_' || g FROM generate_series(1, 1000) g;

INSERT INTO orders (user_id, amount)
SELECT (random() * 999 + 1)::int, (random() * 1000)::numeric
FROM generate_series(1, 50000);

CREATE INDEX orders_user_id_idx ON orders(user_id);
ANALYZE users;
ANALYZE orders;
```

**Шаг 2. Замер без подготовки**

```sql
\timing on

SELECT format(
  'SELECT u.name, count(*), sum(o.amount) FROM users u JOIN orders o ON o.user_id = u.id WHERE u.id = %s GROUP BY u.name;',
  g)
FROM generate_series(1, 1000) g
\gexec

\timing off
```

Запишите итоговое время `Time: ... ms` из вывода psql.

**Шаг 3. Замер с подготовкой**

```sql
PREPARE complex_q(integer) AS
SELECT u.name, count(*), sum(o.amount)
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = $1
GROUP BY u.name;

\timing on

SELECT format('EXECUTE complex_q(%s);', g)
FROM generate_series(1, 1000) g
\gexec

\timing off
```

Запишите итоговое время.

**Шаг 4. Сравните результаты**

| Способ | Суммарное время (мс) | Комментарий |
|:-------|:---------------------|:------------|
| Без подготовки (1000 запросов) | | |
| С подготовкой (1000 `EXECUTE`) | | |

Ответьте на вопросы:
1. Есть ли разница? В какую сторону?
2. Почему для **сложных** запросов выигрыш заметнее, чем для простых?
3. Что произойдёт, если выполнить всего 2–3 запроса? Будет ли подготовка полезна?
4. Помимо скорости, какие ещё преимущества даёт использование подготовленных операторов?

**Шаг 5. Посмотрите счётчики планов**

```sql
SELECT name, generic_plans, custom_plans
FROM pg_prepared_statements
WHERE name = 'complex_q';
```

Объясните, что означают эти счётчики.

**Ожидаемый результат:** вы умеете создавать и использовать подготовленные операторы, видеть их в `pg_prepared_statements` и убедились, что для многократно выполняемых сложных запросов подготовка экономит время на разборе и планировании.

### Задание 5. Курсоры

**Цель:** научиться работать с курсорами для построчного чтения.

**Техническое задание:**

1. В **Сеансе 1** начните транзакцию и объявите курсор:
   ```sql
   BEGIN;
   DECLARE cur CURSOR FOR
   SELECT id, name FROM explain_test ORDER BY id LIMIT 10;
   ```
2. Получите одну строку:
   ```sql
   FETCH cur;
   ```
3. Получите ещё 3 строки:
   ```sql
   FETCH 3 cur;
   ```
4. Получите все оставшиеся строки:
   ```sql
   FETCH ALL cur;
   ```
5. Ещё раз выполните `FETCH cur;` — строк нет (курсор на конце).
6. Закройте курсор и завершите транзакцию:
   ```sql
   CLOSE cur;
   COMMIT;
   ```
7. Объявите курсор, который возвращает **все** строки таблицы (без `LIMIT`), и получите первые 5 строк. Обратите внимание: курсор не загружает все данные в память сразу — он читает их порциями по мере `FETCH`.

**Ожидаемый результат:** вы умеете открывать курсор, читать построчно порциями, закрывать его и понимаете, что курсор работает как «окно» по результату.

**Вопрос для самопроверки:** чем `FETCH` отличается от обычного `SELECT`?
