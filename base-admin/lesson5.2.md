## Тема: Очистка, горизонт очистки, блокировки и статус транзакций

---

## 1. Краткие теоретические сведения

### 1.1. Зачем нужна очистка

Механизм многоверсионности (MVCC) позволяет эффективно реализовать изоляцию на основе снимков, но в результате в табличных страницах **накапливаются старые («мёртвые») версии строк**. Какое-то время исторические версии нужны транзакциям, чтобы они могли работать со своим снимком данных, а в случае отката — вернуться к старым значениям.

Со временем не остаётся ни одного снимка, которому требовалась бы старая версия строки — такая версия называется **«мёртвой»**. Процедура очистки (`VACUUM`) вычищает мёртвые версии строк из табличных страниц и ненужные индексные записи, которые ссылались на такие версии.

Кроме главной задачи, `VACUUM` решает и другие:
- обновляет **карту видимости** (`visibility map`) — отмечает страницы, на которых все версии строк видны во всех снимках;
- обновляет **карту свободного пространства** (`free space map`) — отмечает свободное место в страницах после очистки;
- выполняет **заморозку** (freeze) старых версий строк, чтобы предотвратить переполнение 32-битного счётчика транзакций;
- собирает статистику (если вызван как `VACUUM ANALYZE`).

### 1.2. Горизонт очистки

Для каждой базы данных существует такой номер `xid`, что все исторические версии, удалённые транзакциями с меньшими номерами, **уже не видны ни в одном снимке**. Этот номер называется **горизонтом очистки** (`removable cutoff`).

Всё, что находится «левее» горизонта, можно вычищать; всё, что «правее», ещё может понадобиться какому-то снимку.

**Долгие транзакции и долго выполняющиеся запросы могут удерживать горизонт очистки**, мешая удалять накопившиеся версии строк. Если своевременно не вычищать исторические данные, таблицы и индексы будут разрастаться, занимая лишнее место на диске, а поиск в них актуальных версий строк будет замедляться.

### 1.3. Блокировки

MVCC позволяет обойтись необходимым минимумом блокировок, тем самым увеличивая производительность системы. Основные блокировки устанавливаются **на уровне строк**.

**Блокировки строк:**
- чтение **никогда** не блокирует строки;
- изменение строки блокирует её **для изменений, но не для чтений**;
- единственный случай, когда транзакция будет ждать освобождения блокировки — если она пытается **изменить строку, которая уже изменена другой, ещё не зафиксированной транзакцией**.

**Блокировки таблиц:**
- запрещают изменение или удаление таблицы, пока с ней идёт работа;
- запрещают чтение таблицы при перестроении или перемещении (`VACUUM FULL`, `REINDEX`, некоторые `ALTER TABLE`).

**Время жизни блокировок:**
- устанавливаются по мере необходимости или вручную;
- **автоматически снимаются при завершении транзакции** (`COMMIT` или `ROLLBACK`);
- если блокировка была получена **после** установки точки сохранения (`SAVEPOINT`), она будет снята немедленно при откате к этой точке.

Кроме автоматических блокировок, можно устанавливать **пользовательские (advisory) блокировки** — они не связаны с конкретными объектами БД, а идентифицируются числами, и используются приложением для координации работы.

### 1.4. Статус транзакций (clog)

Для работы многоверсионности серверу надо знать, в каком статусе находится транзакция. Транзакция может быть:
- **активна** (ещё не завершена);
- **зафиксирована** (`COMMIT`);
- **прервана** (`ROLLBACK` или аварийное завершение).

Для представления состояния каждой транзакции требуется **два бита**. Статусы транзакций (commit log, **clog**) хранятся в специальных служебных файлах в каталоге `PGDATA/pg_xact`, а работа с ними происходит в общей памяти, чтобы не обращаться к диску постоянно.

**Ключевой момент:** при любом завершении транзакции (как успешном, так и неуспешном) нужно всего лишь установить соответствующие биты статуса. И фиксация, и обрыв происходят одинаково быстро. **Физического отката данных не происходит**: если прерванная транзакция успела создать новые версии строк, эти версии не уничтожаются. Другие транзакции просто увидят по статусу, что создавшая их транзакция была прервана, и не станут принимать во внимание её изменения. Удалять такие «мёртвые» версии будет `VACUUM`.

### Задание 1. Мёртвые версии строк и `pg_stat_all_tables`

**Цель:** увидеть, что при `UPDATE` и `DELETE` появляются мёртвые версии строк, и научиться их подсчитывать.

**Техническое задание:**

1. В **Сеансе 1** создайте таблицу и заполните её:
   ```sql
   CREATE TABLE vac_test (id integer, note text);
   INSERT INTO vac_test
   SELECT g, 'note_' || g FROM generate_series(1, 10000) g;
   ```
2. Обновите половину строк:
   ```sql
   UPDATE vac_test SET note = note || ' updated' WHERE id <= 5000;
   ```
3. Посмотрите статистику по таблице:
   ```sql
   SELECT relname, n_live_tup, n_dead_tup, n_tup_upd, n_tup_del
   FROM pg_stat_all_tables
   WHERE relname = 'vac_test';
   ```
   Запишите значения полей:
   - `n_live_tup` — количество живых строк;
   - `n_dead_tup` — количество мёртвых строк;
   - `n_tup_upd` — сколько раз строки обновлялись;
   - `n_tup_del` — сколько раз строки удалялись.
4. Удалите 2000 строк:
   ```sql
   DELETE FROM vac_test WHERE id > 8000;
   ```
5. Снова посмотрите статистику. **Вопрос:** как изменились `n_live_tup` и `n_dead_tup`? Объясните, почему.

**Ожидаемый результат:** после `UPDATE` и `DELETE` появились мёртвые версии строк. Их количество растёт с каждой операцией изменения.

**Вопрос для самопроверки:** почему после `UPDATE` количество мёртвых строк увеличилось на количество обновлённых строк?

### Задание 4. Блокировки строк при изменении

**Цель:** увидеть, как одна транзакция блокирует изменение строки другой транзакцией, и как это связано с MVCC.

**Техническое задание:**

1. В **Сеансе 1** создайте таблицу и вставьте строку:
   ```sql
   CREATE TABLE row_lock (id integer, val text);
   INSERT INTO row_lock VALUES (1, 'start');
   ```
2. В **Сеансе 1** начните транзакцию и обновите строку, **не фиксируя**:
   ```sql
   BEGIN;
   UPDATE row_lock SET val = 'from session 1' WHERE id = 1;
   ```
3. В **Сеансе 2** попробуйте обновить ту же строку:
   ```sql
   UPDATE row_lock SET val = 'from session 2' WHERE id = 1;
   ```
   **Вопрос:** что произошло? Почему запрос «завис»?
4. В **Сеансе 1** зафиксируйте транзакцию:
   ```sql
   COMMIT;
   ```
5. Сеанс 2 должен завершить обновление. Проверьте результат:
   ```sql
   SELECT * FROM row_lock;
   ```
   **Вопрос:** какое значение теперь в таблице? Почему?
6. Зафиксируйте изменения в Сеансе 2 (если требуется):
   ```sql
   COMMIT;
   ```
7. **Проверьте, что чтение не блокирует.** В **Сеансе 1** начните транзакцию и обновите строку, не фиксируя:
   ```sql
   BEGIN;
   UPDATE row_lock SET val = 'again from session 1' WHERE id = 1;
   ```
8. В **Сеансе 2** прочитайте строку обычным `SELECT`:
   ```sql
   SELECT * FROM row_lock WHERE id = 1;
   ```
   **Вопрос:** заблокировался ли `SELECT`? Почему чтение не блокируется, хотя строка изменена другой транзакцией?
9. В **Сеансе 1** откатите транзакцию:
   ```sql
   ROLLBACK;
   ```

**Ожидаемый результат:** две транзакции не могут одновременно изменить одну и ту же строку: вторая ждёт завершения первой. Но **чтение не блокируется** — читатель видит старую версию строки из своего снимка, а не ждёт. Это и есть ключевое преимущество MVCC.

**Вопрос для самопроверки:** почему после `COMMIT` в Сеансе 1 значение в таблице стало `'from session 2'`, а не `'from session 1'`?

### Задание 7. Статус транзакций: прерванные транзакции и их «следы»

**Цель:** увидеть, что прерванная транзакция не откатывает физически данные, но её изменения не видны другим транзакциям.

**Техническое задание:**

1. В **Сеансе 1** создайте таблицу и вставьте исходную строку:
   ```sql
   CREATE TABLE abort_test (id integer, val text);
   INSERT INTO abort_test VALUES (1, 'initial');
   ```
2. В **Сеансе 1** начните транзакцию и выполните несколько изменений:
   ```sql
   BEGIN;
   UPDATE abort_test SET val = 'changed in aborted tx' WHERE id = 1;
   INSERT INTO abort_test VALUES (2, 'new row in aborted tx');
   SELECT * FROM abort_test;
   ```
   Запомните, что видит транзакция: изменённую строку `1` и новую строку `2`.
3. В **Сеансе 2** посмотрите на таблицу:
   ```sql
   SELECT * FROM abort_test;
   ```
   **Вопрос:** какие строки видит Сеанс 2? Почему изменения из Сеанса 1 не видны, хотя физически они уже записаны в страницы?
4. В **Сеансе 1** откатите транзакцию:
   ```sql
   ROLLBACK;
   ```
5. В **Сеансе 1** снова посмотрите на таблицу:
   ```sql
   SELECT * FROM abort_test;
   ```
   **Вопрос:** что изменилось? Видна ли строка `2`?
6. Посмотрите на `xmin` и `xmax` строки, которая была изменена:
   ```sql
   SELECT *, xmin, xmax FROM abort_test;
   ```
   У строки `1` `xmin` остался прежним — версия, созданная прерванной транзакцией, физически существует, но не видна из-за статуса транзакции.
7. Посмотрите статистику: сколько мёртвых версий накопилось:
   ```sql
   SELECT n_live_tup, n_dead_tup
   FROM pg_stat_all_tables
   WHERE relname = 'abort_test';
   ```
   **Вопрос:** почему `n_dead_tup > 0`, хотя транзакция была отменена?
8. Выполните `VACUUM` и снова посмотрите статистику — мёртвые версии удалены:
   ```sql
   VACUUM abort_test;
   SELECT n_live_tup, n_dead_tup
   FROM pg_stat_all_tables
   WHERE relname = 'abort_test';
   ```

**Ожидаемый результат:** прерванная транзакция **не откатывает данные физически** — версии строк, созданные ею, остаются в страницах. Но благодаря информации о статусе транзакции (clog) другие транзакции их не видят. Удалить эти «мёртвые» версии может только `VACUUM`.

**Вопрос для самопроверки:** почему фиксация и обрыв транзакции выполняются одинаково быстро?
