## 1. Краткие теоретические сведения

### 1.1. Зачем нужна многоверсионность и как решают эту задачу другие СУБД

Если две транзакции одновременно обращаются к одной и той же строке, возможны разные стратегии:
- блокировать друг друга — но тогда страдает производительность;
- разрешить «грязное чтение» (читать незафиксированные изменения) — но это опасно, ведь изменения могут быть отменены.

PostgreSQL идёт сложным путём: хранит несколько версий одной и той же строки. Пишущая транзакция работает со своей версией, читающая видит свою. Читатели не блокируют писателей, писатели не блокируют читателей.

Другие СУБД решают проблему параллельного доступа по-разному. Условно можно выделить два подхода: пессимистический (блокировки) и оптимистический (многоверсионность, MVCC).

Oracle традиционно использует MVCC на основе сегментов отката (undo segments). При изменении строки Oracle не блокирует читателей: он сохраняет старое значение в undo-сегменте, и читающая транзакция при необходимости восстанавливает из него согласованную версию строки. Блокировки на уровне строк применяются только для операций изменения (INSERT, UPDATE, DELETE), а обычные SELECT не блокируют и не блокируются. Такой подход, как и в PostgreSQL, обеспечивает принцип «читатели не блокируют писателей, писатели не блокируют читателей».

MySQL (InnoDB) также использует MVCC, но в сочетании с традиционным двухфазным блокированием (2PL). InnoDB хранит старые версии строк в undo log и по умолчанию выполняет согласованное неблокирующее чтение (consistent nonlocking read), аналогично Oracle и PostgreSQL. Для операций изменения используются блокировки на уровне строк, а для предотвращения фантомов — gap-блокировки (блокировки промежутков в индексе).

SQL Server исторически придерживается пессимистического подхода: по умолчанию на уровне изоляции READ COMMITTED он устанавливает разделяемые (S) блокировки при чтении, поэтому читатели могут блокировать писателей. Однако начиная с SQL Server 2005 появились уровни изоляции на основе версий строк (SNAPSHOT и READ COMMITTED SNAPSHOT), которые используют хранилище версий в tempdb и позволяют читателям не блокировать писателей. То есть SQL Server поддерживает оба подхода, и выбор зависит от настроек базы данных.

Таким образом, PostgreSQL, Oracle и MySQL (InnoDB) по умолчанию используют MVCC для устранения блокировок между читателями и писателями, а SQL Server по умолчанию склонен к пессимистическим блокировкам, но также поддерживает оптимистический режим через версионирование строк.

### 1.2. Версии строки и время действия

Чтобы отличать версии, каждая из них хранит две отметки «времени действия»:
- xmin — номер транзакции, создавшей версию (команда INSERT);
- xmax — номер транзакции, удалившей или обновившей версию (DELETE или UPDATE). Если xmax = 0, версия актуальна.

В качестве «времени» используются всегда возрастающие номера транзакций (xid). При UPDATE физически выполняется DELETE старой версии и INSERT новой: старая версия получает xmax, новая — свой xmin.

Скрытые столбцы xmin и xmax можно посмотреть в запросе, но в реальной работе их использовать не стоит: это внутренние служебные поля.

### 1.3. Снимок данных

Транзакция, обращаясь к таблице, должна видеть только одну версию каждой строки (или не видеть ни одной). Для этого она работает со снимком данных — согласованным срезом на определённый момент времени.

Снимок — это не физическая копия данных, а всего несколько чисел:
- номер последней зафиксированной транзакции на момент создания снимка;
- список активных транзакций на этот момент (xip).

Список нужен, чтобы исключить из снимка изменения тех транзакций, которые начались до создания снимка, но ещё не были зафиксированы.

Зная эти числа, PostgreSQL всегда может сказать, какая из версий строки будет видна в снимке:
- актуальная (самая последняя зафиксированная) — как правило;
- не самая последняя, если строка удалена и изменение уже зафиксировано, но транзакция ещё продолжает видеть старую версию (работает со своим снимком);
- никакая, если строка удалена до создания снимка.

### 1.4. Уровни изоляции

| Уровень | Поведение в PostgreSQL |
|:--------|:-----------------------|
| Read Uncommitted | Не поддерживается: работает как Read Committed. |
| Read Committed (по умолчанию) | Снимок строится на момент начала каждого оператора. Два одинаковых запроса подряд могут показать разные данные. |
| Repeatable Read | Снимок строится на момент начала транзакции (при первом операторе). Все запросы в одной транзакции видят одни и те же данные. Транзакция может завершиться ошибкой сериализации. |
| Serializable | Полная изоляция, как будто транзакция работает одна. Дополнительные накладные расходы. Транзакция может завершиться ошибкой сериализации. |

Уровень задаётся командой:
```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN ISOLATION LEVEL SERIALIZABLE;
```

### 1.5. Классические аномалии изоляции

Стандарт SQL описывает аномалии, которые могут возникать при конкурентном доступе. В PostgreSQL часть из них запрещена на определённых уровнях изоляции, а некоторые — запрещены даже строже, чем требует стандарт.

| Аномалия | Суть | Read Committed (PG) | Repeatable Read (PG) | Serializable (PG) |
|:---|:---|:---:|:---:|:---:|
| Грязное чтение (Dirty Read) | Транзакция читает данные, изменённые другой, ещё не зафиксированной транзакцией | Невозможно | Невозможно | Невозможно |
| Неповторяющееся чтение (Non-repeatable Read) | Повторное чтение той же строки в одной транзакции даёт другой результат, потому что другая транзакция изменила и зафиксировала строку | Возможно | Невозможно | Невозможно |
| Фантомное чтение (Phantom Read) | Повторный запрос с условием возвращает новый набор строк из-за вставки или удаления строк другой зафиксированной транзакцией | Возможно | Невозможно* | Невозможно |
| Потерянное обновление (Lost Update) | Две транзакции читают одно значение, затем обе обновляют строку на основе прочитанного; одно изменение «теряется» | Возможно (на уровне приложения) | Невозможно | Невозможно |
| Аномалия сериализации (Serialization Anomaly) | Результат параллельного выполнения не соответствует ни одному последовательному порядку транзакций | Возможно | Возможно | Невозможно |

\* Стандарт SQL допускает фантомное чтение на Repeatable Read, но PostgreSQL его не допускает — это более строгая гарантия, чем требует стандарт.

Важно про потерянное обновление. В PostgreSQL на уровне Read Committed СУБД не «теряет» обновление сама по себе: если две транзакции выполняют UPDATE одной и той же строки, вторая дождётся завершения первой и перечитает строку. Потерянное обновление возникает, когда приложение читает значение, а затем использует его в UPDATE как константу, не перечитывая строку. Это классическая ошибка логики приложения, и СУБД не может её предотвратить, потому что не знает, что прочитанное значение связано с обновляемым столбцом.

### Задание 1. Версии строки: xmin и xmax

**Цель:** увидеть, что при изменении строки создаётся новая версия, а старая остаётся доступной другим транзакциям.

**Техническое задание:**

1. В Сеансе 1 создайте таблицу и вставьте строку (команда выполнится в режиме автофиксации):
   ```sql
   CREATE TABLE t (s text);
   INSERT INTO t VALUES ('Первая версия');
   ```
2. Посмотрите на скрытые столбцы:
   ```sql
   SELECT *, xmin, xmax FROM t;
   ```
   Запишите значения xmin и xmax. xmax = 0 означает, что версия актуальна.

3. В Сеансе 2 начните транзакцию и запомните её номер:
   ```sql
   BEGIN;
   SELECT pg_current_xact_id();
   ```
   Запишите номер (пусть, например, 737).

4. В Сеансе 2, не завершая транзакцию, измените строку:
   ```sql
   UPDATE t SET s = 'Вторая версия';
   SELECT *, xmin, xmax FROM t;
   ```
   **Вопрос:** как изменились xmin и xmax? Почему?

5. В Сеансе 1 посмотрите на строку:
   ```sql
   SELECT *, xmin, xmax FROM t;
   ```
   **Вопрос:** что видит Сеанс 1? Что означает значение в xmax? Почему s остаётся «Первая версия»?

6. В Сеансе 2 зафиксируйте транзакцию:
   ```sql
   COMMIT;
   ```
7. В Сеансе 1 снова выполните:
   ```sql
   SELECT *, xmin, xmax FROM t;
   ```
   **Вопрос:** что изменилось? Почему теперь видна вторая версия?

**Ожидаемый результат:** вы увидели, что новая версия строки создаётся с новым xmin, а старая получает xmax. Пока транзакция не зафиксирована, её изменения не видны другим транзакциям.

**Вопрос для самопроверки:** почему UPDATE в PostgreSQL фактически является комбинацией DELETE и INSERT?

### Задание 4. Внутреннее устройство снимка

**Цель:** увидеть, что снимок — это несколько чисел, и научиться их читать.

**Техническое задание:**

1. В Сеансе 1 выполните:
   ```sql
   SELECT pg_current_snapshot();
   ```
   Функция возвращает снимок в формате xmin:xmax:xip_list, где:
   - xmin — самый старый номер активной транзакции, которая ещё видна;
   - xmax — номер первой транзакции, которая ещё не была запущена на момент снимка;
   - xip_list — список активных (незавершённых) транзакций.

2. Разберите снимок по компонентам:
   ```sql
   SELECT
     pg_snapshot_xmin(pg_current_snapshot()) AS xmin,
     pg_snapshot_xmax(pg_current_snapshot()) AS xmax,
     pg_snapshot_xip(pg_current_snapshot()) AS xip;
   ```
   Объясните, что означает каждое значение.

3. В Сеансе 1 начните транзакцию:
   ```sql
   BEGIN;
   SELECT pg_current_xact_id();
   ```

4. В Сеансе 2 начните вторую транзакцию:
   ```sql
   BEGIN;
   SELECT pg_current_xact_id();
   ```

5. В Сеансе 1 снова посмотрите снимок:
   ```sql
   SELECT pg_current_snapshot();
   ```
   **Вопрос:** появился ли номер транзакции Сеанса 2 в списке активных (xip)? Почему?

6. Посмотрите, какой снимок «держит» каждый backend:
   ```sql
   SELECT pid, backend_xmin, state
   FROM pg_stat_activity
   WHERE backend_type = 'client backend';
   ```
   backend_xmin — это самый старый xmin, который нужен данному backend'у для его снимка. Пока транзакция активна, этот xmin удерживает горизонт очистки: старые версии строк не могут быть удалены.

7. Завершите транзакции в обоих сеансах:
   ```sql
   COMMIT;
   ```

**Ожидаемый результат:** вы понимаете, что снимок — это не копия данных, а набор чисел (xmin, xmax, xip), и что активные транзакции удерживают горизонт очистки.

**Вопрос для самопроверки:** почему долгая транзакция мешает очистке (VACUUM) удалять мёртвые версии строк?

### Задание 5. Serializable

**Цель:** познакомиться с уровнем полной изоляции и увидеть, что он тоже может завершаться ошибкой сериализации.

   ```sql
   CREATE TABLE ser_test (id integer PRIMARY KEY, val integer);
   INSERT INTO ser_test VALUES (1, 10), (2, 20);
   ```

2. В Сеансе 1 начните транзакцию:
   ```sql
   BEGIN ISOLATION LEVEL SERIALIZABLE;
   SELECT sum(val) FROM ser_test;
   ```
   Запомните результат (должно быть 30).

3. В Сеансе 2 начните транзакцию:
   ```sql
   BEGIN ISOLATION LEVEL SERIALIZABLE;
   SELECT sum(val) FROM ser_test;
   ```

4. В Сеансе 1 вставьте строку, которая меняет сумму:
   ```sql
   INSERT INTO ser_test VALUES (3, 30);
   ```
5. В Сеансе 1 зафиксируйте транзакцию:
   ```sql
   COMMIT;
   ```
6. В Сеансе 2 вставьте свою строку:
   ```sql
   INSERT INTO ser_test VALUES (4, 40);
   ```
   **Вопрос:** что произошло? Прочитайте сообщение об ошибке. Это ошибка сериализации, потому что транзакции «конфликтуют» по предикату (sum).

   ```sql
   SELECT * FROM ser_test ORDER BY id;
   ```

**Ожидаемый результат:** на уровне Serializable PostgreSQL обнаруживает конфликт и прерывает одну из транзакций, чтобы сохранить полную изоляцию. Приложение должно повторить транзакцию.

**Вопрос для самопроверки:** почему на уровне Serializable конфликт обнаруживается, хотя транзакции работают с разными строками?

### Задание 6. Воспроизведение классических аномалий

**Техническое задание:**

Все шаги выполняются в двух параллельных сеансах psql (Сеанс 1 и Сеанс 2). Если сеансы ещё не открыты — откройте их.

#### Часть A. Грязное чтение — доказательство, что его нет

1. В Сеансе 1 создайте таблицу и заполните её:
   ```sql
   DROP TABLE IF EXISTS anomaly;
   CREATE TABLE anomaly (id integer PRIMARY KEY, val integer);
   INSERT INTO anomaly VALUES (1, 100);
   ```

2. В Сеансе 1 начните транзакцию и измените строку, не фиксируя:
   ```sql
   BEGIN;
   UPDATE anomaly SET val = 999 WHERE id = 1;
   ```

3. В Сеансе 2 выполните запрос:
   ```sql
   SELECT val FROM anomaly WHERE id = 1;
   ```
   **Вопрос:** какое значение видит Сеанс 2 — 100 или 999? Почему?

4. В Сеансе 1 откатите транзакцию:
   ```sql
   ROLLBACK;
   ```

5. Снова проверьте значение в Сеансе 2 — оно должно остаться 100.

**Ожидаемый результат:** Сеанс 2 никогда не видит незафиксированное значение 999. Грязное чтение в PostgreSQL невозможно ни на одном уровне изоляции.

#### Часть B. Неповторяющееся чтение

1. Восстановите исходное значение (в любом сеансе, автофиксация):
   ```sql
   UPDATE anomaly SET val = 100 WHERE id = 1;
   ```

2. В Сеансе 1 начните транзакцию (по умолчанию Read Committed) и прочитайте строку:
   ```sql
   BEGIN;
   SELECT val FROM anomaly WHERE id = 1;
   ```
   Запомните результат (100).

3. В Сеансе 2 обновите строку и зафиксируйте изменение:
   ```sql
   UPDATE anomaly SET val = 200 WHERE id = 1;
   ```

4. В Сеансе 1, не завершая транзакцию, снова выполните тот же запрос:
   ```sql
   SELECT val FROM anomaly WHERE id = 1;
   ```
   **Вопрос:** какое значение теперь? Это и есть неповторяющееся чтение: один и тот же запрос в одной транзакции дал разные результаты.

5. Завершите транзакцию в Сеансе 1 (COMMIT;).

6. Повторите шаги 2–4, но в Сеансе 1 начните транзакцию с уровнем Repeatable Read:
   ```sql
   BEGIN ISOLATION LEVEL REPEATABLE READ;
   SELECT val FROM anomaly WHERE id = 1;
   ```
   После обновления в Сеансе 2 снова выполните SELECT в Сеансе 1. **Вопрос:** изменился ли результат? Почему?

**Ожидаемый результат:** на Read Committed значение меняется; на Repeatable Read — остаётся прежним (снимок фиксируется в начале транзакции).

#### Часть C. Фантомное чтение

1. В Сеансе 1 создайте таблицу и заполните её:
   ```sql
   DROP TABLE IF EXISTS phantom;
   CREATE TABLE phantom (id integer PRIMARY KEY, amount integer);
   INSERT INTO phantom VALUES (1, 100), (2, 200);
   ```

2. В Сеансе 1 начните транзакцию (Read Committed) и посчитайте строки с условием:
   ```sql
   BEGIN;
   SELECT count(*) FROM phantom WHERE amount > 50;
   ```
   Запомните результат (2).

3. В Сеансе 2 вставьте новую строку, подходящую под условие, и зафиксируйте:
   ```sql
   INSERT INTO phantom VALUES (3, 300);
   ```

4. В Сеансе 1 снова выполните тот же запрос:
   ```sql
   SELECT count(*) FROM phantom WHERE amount > 50;
   ```
   **Вопрос:** сколько строк теперь? Появилась «фантомная» строка.

5. Завершите транзакцию (COMMIT;).

6. Повторите шаги 2–4, но в Сеансе 1 используйте Repeatable Read:
   ```sql
   BEGIN ISOLATION LEVEL REPEATABLE READ;
   SELECT count(*) FROM phantom WHERE amount > 50;
   ```
   После вставки в Сеансе 2 снова выполните запрос в Сеансе 1. **Вопрос:** изменилось ли количество? Почему?

**Ожидаемый результат:** на Read Committed фантом появляется; на Repeatable Read — нет. PostgreSQL запрещает фантомы на Repeatable Read, хотя стандарт SQL это допускает.

#### Часть D. Потерянное обновление (на уровне приложения)

1. В Сеансе 1 создайте таблицу и заполните её:
   ```sql
   DROP TABLE IF EXISTS lost;
   CREATE TABLE lost (id integer PRIMARY KEY, amount numeric);
   INSERT INTO lost VALUES (1, 800.00);
   ```

2. В Сеансе 1 начните транзакцию и прочитайте значение:
   ```sql
   BEGIN;
   SELECT amount FROM lost WHERE id = 1;
   ```
   Запомните результат (800.00).

3. В Сеансе 2 тоже начните транзакцию и прочитайте то же значение:
   ```sql
   BEGIN;
   SELECT amount FROM lost WHERE id = 1;
   ```
   Тоже 800.00.

4. В Сеансе 1 обновите строку, используя ранее прочитанное значение (а не перечитывая строку):
   ```sql
   UPDATE lost SET amount = 800.00 + 100 WHERE id = 1;
   COMMIT;
   ```
   Теперь в таблице 900.00.

5. В Сеансе 2 обновите строку, тоже используя ранее прочитанное значение 800.00:
   ```sql
   UPDATE lost SET amount = 800.00 + 100 WHERE id = 1;
   COMMIT;
   ```
   **Вопрос:** какое значение в таблице после этого? Проверьте:
   ```sql
   SELECT amount FROM lost WHERE id = 1;
   ```
   Результат — снова 900.00. Изменение, сделанное Сеансом 1, потеряно. Приложение «не знало», что значение уже изменилось, потому что использовало устаревшее прочитанное значение.

6. Как предотвратить? Покажите два способа:
   - Перечитывать строку в UPDATE: вместо SET amount = 800.00 + 100 писать SET amount = amount + 100. Тогда PostgreSQL сам перечитает актуальное значение:
     ```sql
     -- Восстановите 800.00 и повторите эксперимент с SET amount = amount + 100
     ```
   - Использовать SELECT ... FOR UPDATE: блокировать строку при чтении, чтобы другая транзакция не смогла её изменить:
     ```sql
     BEGIN;
     SELECT amount FROM lost WHERE id = 1 FOR UPDATE;
     -- теперь другая транзакция будет ждать
     UPDATE lost SET amount = amount + 100 WHERE id = 1;
     COMMIT;
     ```

**Ожидаемый результат:** вы увидели, что потерянное обновление — это ошибка логики приложения, а не «вина» СУБД. Его можно предотвратить перечитыванием строки в UPDATE или блокировкой через FOR UPDATE.

#### Часть E. Аномалия сериализации (по желанию)

Если останется время, можно показать аномалию сериализации на уровне Repeatable Read (write skew):

1. Создайте таблицу:
   ```sql
   CREATE TABLE on_call (doctor text PRIMARY KEY, on_call boolean);
   INSERT INTO on_call VALUES ('Alice', true), ('Bob', true);
   ```
2. В Сеансе 1 (Repeatable Read) проверьте, что оба врача на смене:
   ```sql
   BEGIN ISOLATION LEVEL REPEATABLE READ;
   SELECT count(*) FROM on_call WHERE on_call = true;
   ```
   Результат 2.
3. В Сеансе 2 (Repeatable Read) сделайте то же самое:
   ```sql
   BEGIN ISOLATION LEVEL REPEATABLE READ;
   SELECT count(*) FROM on_call WHERE on_call = true;
   ```
   Тоже 2.
4. В Сеансе 1 снимите с дежурства одного врача (предполагая, что второй остаётся):
   ```sql
   UPDATE on_call SET on_call = false WHERE doctor = 'Alice';
   COMMIT;
   ```
5. В Сеансе 2 снимите с дежурства другого:
   ```sql
   UPDATE on_call SET on_call = false WHERE doctor = 'Bob';
   COMMIT;
   ```
6. Проверьте результат:
   ```sql
   SELECT count(*) FROM on_call WHERE on_call = true;
   ```
   Результат 0 — никто не на смене. Это аномалия сериализации: каждая транзакция видела, что на смене двое, и считала, что можно снять одного. Вместе они нарушили инвариант.

**Ожидаемый результат:** на Repeatable Read аномалия сериализации возможна. На Serializable PostgreSQL обнаружил бы конфликт и прервал одну из транзакций с ошибкой could not serialize access due to read/write dependencies among transactions.
