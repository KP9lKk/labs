# Лабораторная работа № 4.2

## Тема: Процессы, память, хранение данных и расширяемость PostgreSQL

---

## 1. Краткие теоретические сведения

### 1.1. Процессы сервера

При старте PostgreSQL запускается процесс **postmaster**. Он запускает все остальные процессы (в Unix — через системный вызов `fork`) и «присматривает» за ними: если какой-либо процесс завершится аварийно, postmaster перезапустит его (или весь сервер, если решит, что процесс мог повредить общие данные).

**Обслуживающий процесс (backend)** порождается для каждого нового клиента. Postmaster слушает входящие соединения, а для нового клиента создаёт backend, и дальше клиент общается уже с ним. Backend, в том числе, выполняет аутентификацию.

**Фоновые процессы:**
- `checkpointer` — выполняет контрольные точки (сбрасывает все грязные буферы на диск);
- `background writer` — сбрасывает часть грязных буферов, которые скоро будут вытеснены;
- `walwriter` — асинхронно записывает журнал предзаписи (WAL) на диск;
- `autovacuum launcher` — запускает рабочие процессы автоочистки;
- `logical replication launcher` — запускает процессы логической репликации.

### 1.2. Память: общая и локальная

Postmaster выделяет **общую память**, доступную всем процессам. В ней располагаются:
- **буферный кеш** (`shared_buffers`) — страницы данных, прочитанные с диска;
- WAL-буферы;
- информация о блокировках, статусах транзакций и т.п.

Кроме общей памяти, каждый процесс имеет **локальную память**, доступную только ему. В ней выделяется место для:
- разобранных запросов и их планов;
- состояния открытых курсоров (порталов);
- кеша системного каталога;
- места для сортировки, хеширования (параметр `work_mem`).

При большом числе клиентов применяют **пул соединений** (например, pgBouncer): клиенты подключаются к менеджеру пула, а тот держит фиксированное число соединений с сервером. При этом несколько клиентов разделяют один backend и его локальное состояние — это надо учитывать при разработке приложений (например, подготовленные операторы видны всем клиентам, разделяющим backend).

### 1.3. Хранение данных: страницы и файлы

Данные хранятся в обычных файлах операционной системы. Логически файлы разделены на **страницы** (иногда говорят «блок»). Обычно страница имеет размер **8 КБ**. Размер можно изменить (16 или 32 КБ), но только при сборке сервера — собранный и запущенный кластер работает со страницами только одного размера.

Каждая страница имеет **заголовок** и **полезные данные**; между ними может находиться свободное пространство, если страница занята не полностью.

Каждый объект (таблица, индекс) представлен **несколькими слоями (forks)**:
- **main** — собственно данные;
- **fsm** (free space map) — карта свободного пространства;
- **vm** (visibility map) — карта видимости (только для таблиц);
- **init** — «пустышка» для основного слоя (используется при сбое; только для нежурналируемых таблиц).

Слой состоит из одного или нескольких файлов-сегментов. Когда файл достигает **1 ГБ**, создаётся следующий файл этого же слоя. Порядковый номер сегмента добавляется в конец имени файла.

### 1.4. TOAST

Любая версия строки в PostgreSQL должна целиком помещаться на одну страницу. Для «длинных» версий строк применяется технология **TOAST** (The Oversized Attributes Storage Technique):
- значение поля может быть **сжато**, чтобы версия строки поместилась на страницу;
- значение может быть **вынесено** в отдельную служебную таблицу;
- могут применяться **оба подхода** одновременно.

Для каждой основной таблицы при необходимости создаётся отдельная **TOAST-таблица** (и к ней специальный индекс). Такие таблицы и индексы располагаются в отдельной схеме `pg_toast` и поэтому обычно не видны (для временных таблиц используется схема `pg_toast_temp_N`).

TOAST-таблица читается только при обращении к «длинному» полю. Для неё поддерживается своя версионность: если обновление данных не затрагивает «длинное» значение, новая версия строки будет ссылаться на то же самое значение в TOAST-таблице — это экономит место.

Стратегии работы с длинными значениями (`Storage`):
- `plain` — TOAST не применяется (тип фиксированной длины);
- `extended` — сжатие + отдельное хранение;
- `external` — только отдельное хранение (без сжатия);
- `main` — сжатие в приоритете, вынос — только если сжатия недостаточно.

### 1.5. Буферный кеш и журнал предзаписи (WAL)

**Буферный кеш** (`shared_buffers`) располагается в общей памяти, чтобы все процессы имели к нему доступ. Любая работа со страницами данных проходит через кеш: процесс ищет страницу в кеше, а при отсутствии — просит ОС прочитать её и помещает в кеш. Изменённые страницы становятся «грязными» и записываются на диск асинхронно.

Размер буферного кеша обычно не позволяет поместить всю базу, поэтому применяется **вытеснение** по алгоритму LRU (Least Recently Used) — вытесняется страница, которая использовалась реже других.

PostgreSQL работает с дисками через операционную систему, у которой тоже есть свой кеш. Если страница не найдена в буферном кеше, она может найтись в кеше ОС — тогда обращение к диску удастся избежать.

При сбое содержимое оперативной памяти пропадает, изменённые, но ещё не записанные данные теряются. Это противоречит свойству долговечности. Поэтому PostgreSQL ведёт **журнал предзаписи (WAL)**: при выполнении операции формируется запись, содержащая минимально необходимую информацию для повторного выполнения операции. Эта запись должна попасть на диск **раньше**, чем будут записаны изменяемые данные.

Файлы WAL расположены в каталоге `PGDATA/pg_wal` и по умолчанию имеют размер 16 МБ (задаётся при инициализации кластера).

**Контрольная точка** — периодический сброс всех грязных буферов на диск. Она гарантирует, что все изменения до контрольной точки находятся на диске, и ограничивает размер журнала, необходимого для восстановления. Восстановление после сбоя начинается с последней завершённой контрольной точки.

### 1.6. Расширяемость

PostgreSQL спроектирован с расчётом на расширяемость: можно создавать новые типы данных на основе существующих, писать хранимые подпрограммы, создавать новые типы индексов, запускать служебные фоновые процессы, подключаться к внешним источникам данных. Большинство расширений устанавливается «на лету», без перезапуска сервера.

```sql
CREATE EXTENSION имя;
SELECT * FROM pg_available_extensions;
SELECT * FROM pg_extension;
```

## 2. Порядок выполнения работы

**Подготовка.** Запустите контейнер PostgreSQL с примонтированным каталогом данных, чтобы можно было видеть файлы на хосте:

```bash
mkdir -p ~/pg_storage_lab
docker run -d --name pg-storage \
  -e POSTGRES_PASSWORD=storpass \
  -p 5432:5432 \
  -v ~/pg_storage_lab:/var/lib/postgresql/data \
  postgres:latest
```

Проверьте работу:
```bash
docker ps
```

Подключитесь к psql:
```bash
docker exec -it pg-storage psql -U postgres
```

> **Примечание.** Некоторые команды выполняются в терминале хоста (через `docker exec`), другие — внутри psql. В тексте это указано явно.

### Задание 1. Процессы сервера

**Цель:** увидеть, какие процессы работают внутри контейнера, и понять их назначение.

**Техническое задание:**

1. В терминале хоста выведите список процессов PostgreSQL:
   ```bash
   docker exec -it pg-storage ps aux | grep postgres
   ```

   - `postmaster` (главный процесс);
   - `checkpointer`;
   - `background writer`;
   - `walwriter`;
   - `autovacuum launcher`;


5. Откройте второй терминал и подключитесь к контейнеру **ещё раз** (`docker exec -it pg-storage psql -U postgres`). Снова выполните запрос из п.4 — теперь вы видите **два** backend'а. Это демонстрирует, что для каждого клиента создаётся отдельный процесс.

### Задание 2. Общая и локальная память

**Цель:** понять, чем отличается общая память от локальной, и как параметры влияют на выполнение запросов.

**Техническое задание:**

1. В **psql** посмотрите параметры памяти:
   ```sql
   SHOW shared_buffers;
   SHOW work_mem;
   SHOW maintenance_work_mem;
   ```
   Запишите значения.

2. Посмотрите, к какой категории (`context`) относятся эти параметры:
   ```sql
   SELECT name, setting, unit, context
   FROM pg_settings
   WHERE name IN ('shared_buffers', 'work_mem', 'maintenance_work_mem');
   ```
   Объясните, что означает значение `context` для каждого параметра.

3. Создайте таблицу с данными, достаточными для сортировки:
   ```sql
   CREATE TABLE mem_test (id integer, val text);
   INSERT INTO mem_test
   SELECT g, 'value_' || g FROM generate_series(1, 100000) g;
   ANALYZE mem_test;
   ```

4. Посмотрите план запроса с сортировкой:
   ```sql
   EXPLAIN (ANALYZE)
   SELECT * FROM mem_test ORDER BY val;
   ```
   Найдите узел `Sort`. Обратите внимание на строку `Sort Method: quicksort` — это значит, что сортировка выполнена в памяти (`work_mem` хватило). Параметр `Memory: ...kB` показывает, сколько памяти использовано.

5. Уменьшите `work_mem` для текущего сеанса и повторите запрос:
   ```sql
   SET work_mem = '64kB';
   EXPLAIN (ANALYZE)
   SELECT * FROM mem_test ORDER BY val;
   ```
   **Вопрос:** изменился ли `Sort Method`? Появилась ли строка `external merge Disk`? Что это означает?

6. Сбросьте параметр:
   ```sql
   RESET work_mem;
   ```

**Ожидаемый результат:** вы понимаете, что `shared_buffers` — общая память, `work_mem` — локальная, и что недостаток `work_mem` приводит к сбросу сортировки на диск.

**Вопрос для самопроверки:** почему `work_mem` не стоит делать слишком большим?

### Задание 3. Хранение данных: страницы и слои

**Цель:** увидеть, как таблица представлена в файловой системе.

**Техническое задание:**


   ```sql
   SELECT pg_relation_filepath('storage_test');
   ```

   Подставьте свои значения. Вы должны увидеть основной файл, а также файлы `_fsm` и `_vm` (они могли появиться после первой модификации).

   ```sql
   SELECT pg_size_pretty(pg_total_relation_size('storage_test'));
   ```

7. Вставьте **длинную строку** (более 8 КБ) — сработает TOAST:

   ```sql
   SELECT relname, reltoastrelid

   ```
   `reltoastrelid` — это OID TOAST-таблицы. Получите путь к её файлу:
   ```sql
   SELECT pg_relation_filepath('pg_toast_' || reltoastrelid)
   ```

11. Посмотрите стратегии хранения для столбцов:

    Обратите внимание на столбец `Storage` (для `text` обычно `extended`).

12. Измените стратегию для столбца `data`:

    Проверьте, что изменение применилось:
    ```sql
    \d+ storage_test
    ```

**Ожидаемый результат:** вы понимаете, что таблица — это набор файлов (слоёв), а длинные значения выносятся в отдельную TOAST-таблицу. Стратегию работы с длинными значениями можно менять.

### Задание 4. Буферный кеш и `EXPLAIN (BUFFERS)`

**Цель:** увидеть, как буферный кеш влияет на выполнение запроса.

**Техническое задание:**

1. В **psql** создайте таблицу и заполните её:
   ```sql
   CREATE TABLE buf_test (id integer, val text);
   INSERT INTO buf_test

   ```

2. Выполните запрос с информацией о буферах:
   ```sql
   EXPLAIN (ANALYZE, BUFFERS)
   SELECT * FROM buf_test;
   ```
   В выводе найдите строку `Buffers: shared hit=... read=... dirtied=...`. Пояснение:
   - `hit` — количество страниц, найденных в буферном кеше;
   - `read` — количество страниц, прочитанных с диска (или из кеша ОС);
   - `dirtied` — количество страниц, которые были изменены запросом (для `SELECT` обычно 0).

3. Запишите значения `hit` и `read`.

4. Выполните тот же запрос ещё раз:
   ```sql
   EXPLAIN (ANALYZE, BUFFERS)
   SELECT * FROM buf_test;
   ```
   Сравните с предыдущим результатом. **Вопрос:** почему изменилось соотношение `hit` и `read`?

5. Перезапустите контейнер, чтобы сбросить буферный кеш:
   ```bash
   docker restart pg-storage
   ```
   Подождите несколько секунд. Подключитесь снова:
   ```bash
   docker exec -it pg-storage psql -U postgres
   ```

6. Выполните тот же запрос ещё раз. **Вопрос:** что произошло с `read`? Почему?

7. Посмотрите текущую позицию журнала WAL:

9. Снова посмотрите позицию журнала:
   ```sql
   SELECT pg_current_wal_lsn();
   ```

   **Вопрос:** изменилась ли позиция? Что это означает?

10. Вычислите, сколько байт сгенерировала операция:

    Подставьте значение из п.7 (в кавычках). Полученное число — размер журнальных записей в байтах.

### Задание 5. Контрольная точка и восстановление

**Цель:** увидеть, как контрольная точка и WAL обеспечивают восстановление после сбоя.

**Техническое задание:**

1. В **psql** выполните контрольную точку вручную:
   ```sql
   CHECKPOINT;
   ```
   Запишите текущую позицию WAL:
   ```sql
   SELECT pg_current_wal_lsn();
   ```

2. Внесите изменения:
   ```sql
   CREATE TABLE crash_test (id integer);
   INSERT INTO crash_test SELECT g FROM generate_series(1, 1000) g;
   DELETE FROM crash_test WHERE id > 500;
   ```

3. **Симулируйте сбой** — убейте процесс postmaster (в терминале хоста):
   ```bash
   docker exec -it pg-storage bash -c "kill -QUIT 1"
   ```
   > `-QUIT` посылает сигнал `SIGQUIT`, который приводит к аварийному завершению postmaster и всех процессов. Это имитация сбоя питания.

4. Контейнер остановится. Проверьте это:
   ```bash
   docker ps -a | grep pg-storage
   ```

5. Запустите контейнер снова:
   ```bash
   docker start pg-storage
   ```

6. Подключитесь к psql и проверьте, что данные восстановлены:
   ```sql
   SELECT count(*) FROM crash_test;
   SELECT min(id), max(id) FROM crash_test;
   ```
   Данные должны быть в том состоянии, в котором были до сбоя.

7. Посмотрите в журнал сообщений сервера:
   ```bash
   docker logs pg-storage | tail -n 30
   ```
   Найдите сообщения о восстановлении (`automatic recovery in progress`, `redo`, `database system is ready to accept connections`).

**Ожидаемый результат:** после аварийного завершения и перезапуска сервер автоматически восстанавливает согласованное состояние с помощью WAL. Все зафиксированные изменения сохранены.

### Задание 6. Расширяемость: установка расширения

**Цель:** научиться устанавливать и использовать расширения.

**Техническое задание:**

1. В **psql** посмотрите список доступных расширений:
   ```sql
   SELECT name, default_version, installed_version
   FROM pg_available_extensions
   ORDER BY name
   LIMIT 20;
   ```

2. Установите расширение `hstore` (если оно доступно в образе):
   ```sql
   CREATE EXTENSION hstore;
   ```
   Если `hstore` недоступно, попробуйте `pgcrypto` или `citext`.

3. Проверьте, что расширение установлено:
   ```sql
   SELECT extname, extversion FROM pg_extension;
   ```

4. Используйте функции расширения. Для `hstore`:
   ```sql
   SELECT 'a=>1, b=>2'::hstore;
   ```
   Для `pgcrypto`:
   ```sql
   SELECT digest('Hello, world!', 'md5');
   ```

5. Посмотрите, где на диске расположены файлы расширения:
   ```bash
   docker exec -it pg-storage bash -c "ls /usr/share/postgresql/16/extension/ | grep hstore"
   ```
   (замените `hstore` на имя вашего расширения и `16` на версию PostgreSQL).

6. Удалите расширение (если больше не нужно):
   ```sql
   DROP EXTENSION hstore;  -- или другое
   ```

**Ожидаемый результат:** вы умеете устанавливать расширения, использовать их функции и видеть их в каталоге.

**Вопрос для самопроверки:** почему большинство расширений не требуют перезапуска сервера?
