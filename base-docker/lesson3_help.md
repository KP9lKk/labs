## Справка к заданию 1. Что такое `pg_settings` и `pg_file_settings`

**`pg_settings`** — это «пульт управления» PostgreSQL. В нём видно:
- `name` — имя параметра;
- `setting` — текущее действующее значение;
- `unit` — единица измерения, если есть;
- `source` — откуда взято значение: `default`, `configuration file`, `database`, `session`, `override` и т.д.;
- `sourcefile`, `sourceline` — из какого файла и строки взято значение;
- `context` — когда параметр можно менять: `internal`, `postmaster`, `sighup`, `superuser`, `user`;
- `pending_restart` — `true`, если значение уже записано в файл, но применится только после перезапуска.

**`pg_file_settings`** — это «сырой» список строк из файлов конфигурации. Здесь можно увидеть:
- `sourcefile`, `sourceline` — где именно в файле найдена строка;
- `name`, `setting` — параметр и значение;
- `applied` — будет ли строка применена (`t`/`f`);
- `error` — текст ошибки, если строка некорректна.

Проще говоря: `pg_settings` показывает, **что сейчас действует**, а `pg_file_settings` показывает, **что написано в файлах** и нет ли там ошибок.

## Справка к заданию 2. Что настраивается через `ALTER SYSTEM`

В этом задании настраивается **`work_mem`** — объём памяти для одной операции сортировки или хеширования внутри запроса. Подробнее см. задание 9.

`ALTER SYSTEM SET work_mem = '16MB';` не меняет значение мгновенно. Команда записывает настройку в файл `postgresql.auto.conf`. Чтобы PostgreSQL перечитал этот файл без перезапуска, нужно выполнить `SELECT pg_reload_conf();`.

Важно:
- `postgresql.auto.conf` всегда находится в каталоге данных;
- он читается после `postgresql.conf` и имеет приоритет;
- вручную его редактировать не рекомендуется — для этого есть `ALTER SYSTEM`.

`ALTER SYSTEM RESET work_mem;` удаляет настройку из `postgresql.auto.conf`, после чего снова начинает действовать значение из `postgresql.conf` или значение по умолчанию.

## Справка к заданию 3. Что настраивается через `postgresql.conf` и `include_dir`

В этом задании снова настраивается **`work_mem`**, но уже через основной файл `postgresql.conf` и дополнительный файл в каталоге `conf.d`.

**`postgresql.conf`** — главный файл конфигурации PostgreSQL. В нём обычно лежат основные настройки.

**`include_dir`** — директива, которая говорит: «подключи все `.conf`-файлы из указанного каталога». Это удобно, чтобы не хранить все настройки в одном огромном файле.

Например:
```conf
include_dir = 'conf.d'
```

Если в `conf.d/work_mem.conf` написано:
```conf
work_mem = '24MB'
```
то после `pg_reload_conf()` PostgreSQL увидит эту настройку. В `pg_file_settings` будет видно, что значение пришло именно из `work_mem.conf`.

## Справка к заданию 4. Что настраивается и как искать ошибку

В этом задании настраивается **`max_connections`** — максимальное число одновременных подключений к серверу. Подробнее см. задание 9.

Если в файле конфигурации написано некорректное значение, например:
```conf
max_connections = abc
```
то:
- `pg_file_settings` покажет строку с `error`;
- `applied` будет `f`;
- при попытке перезапуска сервер может не запуститься;
- в логах контейнера будет ошибка вида `invalid value for parameter "max_connections"`.

Исправлять такие ошибки можно через bind mount: файл на хосте доступен внутри контейнера. После исправления контейнер нужно запустить снова.

## Справка к заданию 5. Что настраивается на уровне базы и роли

В этом задании настраиваются:
- **`work_mem`** для базы данных `cfg_db`;
- **`search_path`** для роли `cfg_user`.

`ALTER DATABASE cfg_db SET work_mem = '32MB';` означает: все сеансы, которые подключаются к базе `cfg_db`, получат `work_mem = 32MB`, если не переопределят его позже.

`ALTER ROLE cfg_user SET search_path = public, app;` означает: когда пользователь `cfg_user` подключается, PostgreSQL будет искать объекты сначала в схеме `public`, потом в `app`, если имя объекта не указано явно.

**`search_path`** — это список схем, в которых PostgreSQL ищет таблицы, функции, типы и другие объекты. Например, если написать `SELECT * FROM users;`, PostgreSQL будет искать таблицу `users` в схемах из `search_path` по порядку.

Настройки базы и роли хранятся в системной таблице `pg_db_role_setting`.

## Справка к заданию 6. Что настраивается в сеансе и транзакции

В этом задании настраивается **`work_mem`** на разных уровнях:
- `SET work_mem = '64MB';` — до конца текущего сеанса;
- `SET LOCAL work_mem = '128MB';` — только до конца текущей транзакции;
- `RESET work_mem;` — сброс к значению, которое было бы по умолчанию/из настроек.

Ключевая разница:
- `SET` внутри транзакции тоже откатывается при `ROLLBACK`;
- `SET LOCAL` действует только внутри транзакции и исчезает после `COMMIT` или `ROLLBACK`;
- `RESET` возвращает параметр к значению `reset_val`.

Это важно, потому что один и тот же параметр может быть задан на уровне экземпляра, базы, роли и сеанса. Сеанс имеет самый высокий приоритет.

## Справка к заданию 7. Что такое пользовательские параметры

PostgreSQL разрешает создавать свои параметры, если в имени есть точка. Например:
- `myapp.currency_code`
- `myapp.version`

Сам PostgreSQL не использует эти параметры внутри себя. Но приложение может их читать через `current_setting()` и менять через `set_config()` или `SET`.

Пример:
```sql
SELECT set_config('myapp.currency_code', 'RUB', false);
SELECT current_setting('myapp.currency_code');
```

Их можно задать и через `ALTER SYSTEM`:
```sql
ALTER SYSTEM SET myapp.version = '1.0';
SELECT pg_reload_conf();
```

После этого параметр будет виден в сеансах. Это удобно для передачи приложению каких-то настроек без изменения схемы БД.

## Справка к заданию 8. Что такое категории и контекст параметров

В `pg_settings` у каждого параметра есть:
- **`category`** — тематическая группа, например `Connections and Authentication`, `Resource Usage`, `Write-Ahead Log` и т.д.;
- **`context`** — когда и кто может менять параметр.

Основные значения `context`:
- `internal` — нельзя менять;
- `postmaster` — нужно перезапустить сервер;
- `sighup` — можно применить перечитыванием конфигурации;
- `superuser` — может менять суперпользователь;
- `user` — может менять любой пользователь в своём сеансе.

Категории помогают ориентироваться в большом списке параметров, а контекст показывает, как применить изменение: сразу, после `pg_reload_conf()` или только после перезапуска.

## Справка к заданию 9. Подробно по каждому настраиваемому параметру

В этом задании сервер настраивается «как в продуктовой среде». Ниже — справка по каждому параметру простыми словами.

| Параметр | Что это простыми словами | На что влияет | Особенности |
|---|---|---|---|
| `shared_buffers` | Оперативная память, которую сам PostgreSQL использует как кэш для страниц таблиц и индексов. | Чем больше, тем чаще данные читаются из памяти, а не с диска. | Обычно 25% RAM. Это не вся память сервера: ОС тоже кэширует файлы. Требует перезапуска. |
| `effective_cache_size` | Не выделяемая память, а подсказка планировщику: сколько RAM примерно доступно под кэш данных, включая `shared_buffers` и кэш ОС. | Планировщик решает, выгодно ли использовать индекс или лучше читать таблицу последовательно. | Память не резервируется. Обычно 75% RAM. Применяется перечитыванием конфигурации. |
| `work_mem` | Память на одну операцию сортировки или хеширования в одном запросе: `ORDER BY`, `JOIN`, `DISTINCT` и т.п. | Если памяти мало, операция уходит на диск и работает медленнее. Если слишком много — при большом числе соединений может закончиться RAM. | Выделяется не на всё соединение, а на каждый узел плана. Сложный запрос может использовать несколько `work_mem`. Можно менять в сеансе, БД или роли. |
| `maintenance_work_mem` | Память для служебных операций: `VACUUM`, `CREATE INDEX`, `ALTER TABLE ADD FOREIGN KEY` и подобных. | Больше памяти — быстрее обслуживание и создание индексов. | Выделяется на одну операцию, а не на каждое соединение. Обычно ограничивают 1 ГБ. Можно менять без перезапуска. |
| `max_connections` | Максимальное число клиентов, которые могут одновременно подключиться к серверу. | Каждое соединение — это отдельный процесс и дополнительная память. Слишком большое значение вредит. | Нужно оставлять запас для суперпользователя через `superuser_reserved_connections`. Требует перезапуска. |
| `random_page_cost` | Оценка планировщиком стоимости чтения одной случайной страницы с диска относительно последовательного чтения. | Для SSD случайное чтение почти такое же дешёвое, как последовательное. Значение `1.1` заставляет планировщик охотнее выбирать индексы. | Для HDD значение обычно выше, для SSD — около 1.1. Применяется перечитыванием. |
| `effective_io_concurrency` | Сколько одновременных операций ввода-вывода PostgreSQL может держать в работе для некоторых видов доступа. | Для SSD можно ставить больше, для HDD — меньше. Помогает лучше использовать диск. | Это не создаёт потоки само по себе, а настройка поведения. Для SSD часто ставят 200. Применяется перечитыванием. |
| `wal_buffers` | Небольшой буфер в памяти для записей WAL — журнала предзаписи. WAL нужен для восстановления и репликации. | Сглаживает запись журнала на диск. | Обычно 16 МБ достаточно. Может требовать перезапуска; проверяйте `pending_restart`. |
| `max_wal_size` | Мягкий предел, до которого может вырасти объём WAL между контрольными точками. | Больше значение — реже контрольные точки, меньше рывков ввода-вывода, но больше места на диске и дольше восстановление. | Применяется перечитыванием конфигурации. |
| `min_wal_size` | Минимальный объём WAL, который PostgreSQL старается сохранять для повторного использования. | Если WAL становится меньше, старые файлы не удаляются сразу. Помогает сгладить нагрузку. | Применяется перечитыванием конфигурации. |
| `checkpoint_completion_target` | Доля времени между контрольными точками, за которую нужно завершить запись контрольной точки. | `0.9` означает растянуть запись на 90% интервала, чтобы не бить по диску пиками. | Применяется перечитыванием конфигурации. |

### Как читать формулы из задания 9

- `RAM` — общая оперативная память, доступная контейнеру.
- `shared_buffers` — примерно четверть RAM.
- `effective_cache_size` — примерно три четверти RAM, но это только оценка для планировщика.
- `work_mem` — память на одну операцию. Формула даёт безопасный старт, но её можно уточнять под нагрузку.
- `maintenance_work_mem` — память на обслуживание. В формуле есть ограничение сверху: не более 1024 МБ.
- `max_connections` — не меньше 100 и не меньше `4 × CPU`.

### Что проверить после применения

После `ALTER SYSTEM SET ...` и перезапуска/перечитывания выполните:
```sql
SELECT name, setting, unit, source, pending_restart
FROM pg_settings
WHERE name IN (
  'shared_buffers', 'effective_cache_size', 'work_mem',
  'maintenance_work_mem', 'max_connections', 'random_page_cost',
  'effective_io_concurrency', 'wal_buffers', 'max_wal_size',
  'min_wal_size', 'checkpoint_completion_target'
)
ORDER BY name;
```

Если `pending_restart = true`, значит параметр ещё не применился и нужен перезапуск контейнера. Если `source = configuration file`, значение взято из файла конфигурации, как и ожидается.

При сравнении с pgTune различия возможны потому, что pgTune использует свои эвристики и не знает всех особенностей вашей нагрузки. Формулы в лабораторной — учебные, они дают разумный старт, но не заменяют настройку под конкретную систему.
