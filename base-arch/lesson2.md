# Лабораторная работа №2: JIT-компиляция — почему один и тот же байт-код работает с разной скоростью

## Зачем это нужно

В первой лабораторной вы увидели, что Kotlin превращается в байт-код. Но байт-код — это ещё не то, что выполняется на процессоре. JVM может делать с ним две принципиально разные вещи:

- **интерпретировать** — читать инструкцию за инструкцией и выполнять;
- **компилировать** — превращать горячие методы в машинный код, который процессор выполняет напрямую.

Один и тот же `.class` может работать в десятки раз быстрее или медленнее — в зависимости от того, что JVM решила сделать с вашим кодом. Эта лабораторная — про то, чтобы **увидеть этот механизм своими глазами** и перестать верить в магию «JVM сама всё оптимизирует».

Без этого невозможно:

- понимать, почему бенчмарки врут (и как писать их правильно);
- объяснять, почему «одинаковый» код на Java и C++ даёт разную скорость;
- читать логи JIT и понимать, что именно оптимизировалось;
- отвечать на собеседованиях про JIT, tiered compilation и деоптимизацию.

Это прямой мост от первой лабораторной к железу: байт-код → JIT → машинный код → процессор.

## Немного теории перед экспериментами

**Что делает JVM с методом:**

1. Сначала метод **интерпретируется**.
2. JVM считает, сколько раз он вызывался и сколько итераций цикла прошло.
3. Когда счётчик превышает порог — метод попадает в очередь на компиляцию.
4. **C1 (client compiler)** — быстрая компиляция, лёгкие оптимизации.
5. **C2 (server compiler)** — медленная, но агрессивная оптимизация. Включается для «горячих» методов.
6. Иногда C2 ошибается в предположениях — тогда происходит **деоптимизация**, и метод возвращается к интерпретации или C1.

**Уровни компиляции (tiered compilation, по умолчанию включена):**

| Уровень | Что это |
|---|---|
| 0 | Интерпретация |
| 1 | C1 без профилирования |
| 2 | C1 с лёгким профилированием |
| 3 | C1 с полным профилированием |
| 4 | C2 |

Метод может «подниматься» и «опускаться» по этим уровням.

## Эксперименты

### Эксперимент 1. Один код — разная скорость

```kotlin
fun sumArray(arr: IntArray): Long {
    var s = 0L
    for (x in arr) s += x
    return s
}

fun main() {
    val arr = IntArray(10_000_000) { it }
    var total = 0L
    repeat(10) {
        val t = System.nanoTime()
        total += sumArray(arr)
        val ms = (System.nanoTime() - t) / 1_000_000.0
        println("run $it: $ms ms")
    }
    println("total = $total")
}
```

**Задача:**
1. Запустить обычным способом. Записать времена всех 10 прогонов.
2. Запустить с `-Xint`. Записать.
3. Запустить с `-Xcomp`. Записать.
4. Построить таблицу: режим → первый прогон → последний прогон → во сколько раз быстрее.

**Вопросы:**
- Почему в обычном режиме первый прогон медленный, а последующие быстрые?
- Почему `-Xint` стабильно медленный?
- Почему `-Xcomp` может быть быстрее `-Xint`, но медленнее обычного режима на старте?

**Для отчёта:** таблица «режим → время 1-го прогона → время 10-го прогона → ускорение».

### Эксперимент 2. Кто и когда компилируется

```kotlin
fun hot(n: Int): Long {
    var s = 0L
    for (i in 0 until n) s += i
    return s
}

fun cold(n: Int): Long {
    return n.toLong() * 2
}

fun main() {
    repeat(200_000) { hot(100) }
    println(cold(5))
}
```

**Задача:**
1. Запустить с `-XX:+PrintCompilation`.
2. Найти в выводе строки про `hot` и `cold`.
3. Расшифровать формат строки. Пример:
   ```
   123   45       3       Lab2Kt::hot (15 bytes)
   ```
   - первое число — время от старта JVM в мс;
   - второе — номер компиляции по порядку;
   - третье — уровень (1–4);
   - `%` — значит, компиляция «на стеке» (OSR — on-stack replacement, для долгих циклов);
   - `!` — метод с исключениями;
   - `s` — synchronized.

4. Добавить флаги `-XX:+PrintCompilation -XX:+PrintInlining` и посмотреть, что заинлайнилось в `main`.

**Вопросы:**
- Какой метод скомпилировался? Какой нет? Почему?
- Что такое OSR и почему он появляется?
- Сколько времени прошло до первой компиляции?

### Эксперимент 3. Прогрев (warmup) — почему бенчмарки врут

```kotlin
fun work(n: Int): Long {
    var s = 0L
    for (i in 0 until n) {
        s += (i * 31) xor (i shr 3)
    }
    return s
}

fun main() {
    // Прогрев
    repeat(1000) { work(10_000) }

    // Замер
    val t = System.nanoTime()
    var r = 0L
    repeat(100) { r += work(10_000) }
    println("time = ${(System.nanoTime() - t) / 1_000_000} ms, r = $r")
}
```

**Задача:**
1. Запустить **без** прогрева — просто замер сразу.
2. Запустить **с** прогревом (как в коде).
3. Сравнить времена.
4. Убрать прогрев совсем и посмотреть, что будет с первым замером.

**Вопрос:**
- Что такое «warmup» и почему в реальных бенчмарках ему отводят отдельную фазу?
- Почему замер без прогрева показывает завышенное время?
- Что произойдёт, если прогрев будет слишком коротким?

**Дополнительно:** попробуйте прогреть 10, 100, 1000, 10000 итераций и посмотрите, где время стабилизируется.

### Эксперимент 4. Инлайнинг — JIT любит маленькие методы

```kotlin
fun square(x: Int): Int = x * x

fun sumOfSquares(n: Int): Long {
    var s = 0L
    for (i in 0 until n) s += square(i)
    return s
}

fun bigMethod(x: Int): Int {
    var r = x
    r += 1; r *= 2; r -= 3; r = r xor 5
    r += 1; r *= 2; r -= 3; r = r xor 5
    r += 1; r *= 2; r -= 3; r = r xor 5
    r += 1; r *= 2; r -= 3; r = r xor 5
    return r
}

fun main() {
    repeat(100_000) { sumOfSquares(100) }
    repeat(100_000) { bigMethod(7) }
    println("done")
}
```

**Задача:**
1. Запустить с `-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining`.
2. Найти в выводе, что `square` заинлайнился в `sumOfSquares`.
3. Проверить, что `bigMethod` **не** заинлайнился (есть лимит на размер, обычно 35 байт байт-кода для C1 и 325 для C2).
4. Запустить с `-XX:MaxInlineSize=100` и посмотреть, изменилось ли что-то.

**Вопросы:**
- Что такое инлайнинг и зачем он нужен?
- Почему JIT не инлайнит всё подряд?
- Как размер метода влияет на оптимизацию?

**Дополнительно:** посмотрите на свой код из реального проекта. Есть ли методы, которые слишком большие для инлайна?

### Эксперимент 5. Полиморфизм и деоптимизация

```kotlin
open class Animal { open fun sound(): Int = 1 }
class Cat : Animal() { override fun sound(): Int = 2 }
class Dog : Animal() { override fun sound(): Int = 3 }

fun makeSounds(animals: List<Animal>): Long {
    var s = 0L
    for (a in animals) s += a.sound()
    return s
}

fun main() {
    // Мономорфный случай — все Cat
    val cats = List(1_000_000) { Cat() }
    repeat(10) { makeSounds(cats) }

    // Полиморфный случай — Cat и Dog вперемешку
    val mixed = List(1_000_000) { if (it % 2 == 0) Cat() else Dog() }
    repeat(10) { makeSounds(mixed) }

    println("done")
}
```

**Задача:**
1. Запустить с `-XX:+PrintCompilation -XX:+UnlockDiagnosticVMOptions -XX:+TraceDeoptimization` (или `-XX:+PrintDeoptimization` в новых JDK).
2. Найти, что для мономорфного случая JIT делает «мономорфный инлайн» вызова `sound()`.
3. Посмотреть, что происходит с полиморфным случаем: появляются ли `bimorphic`/`megamorphic` вызовы, есть ли деоптимизации.
4. Замерить время обоих случаев.

**Вопросы:**
- Что такое мономорфный, биморфный и мегаморфный вызов?
- Почему полиморфизм может замедлить код, и как JIT с этим борется?
- Что такое деоптимизация и когда она случается?

## Полезные команды

```bash
# Компиляция
kotlinc Lab2.kt -include-runtime -d Lab2.jar

# Обычный запуск
java -jar Lab2.jar

# Только интерпретация (медленно, но предсказуемо)
java -Xint -jar Lab2.jar

# Всё компилировать сразу (быстро, но без профилирования)
java -Xcomp -jar Lab2.jar

# Показать, что компилируется
java -XX:+PrintCompilation -jar Lab2.jar

# Показать инлайнинг (нужны диагностические флаги)
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining -jar Lab2.jar

# Отключить tiered compilation
java -XX:-TieredCompilation -jar Lab2.jar

# Только C1 / только C2
java -XX:TieredStopAtLevel=1 -jar Lab2.jar
java -XX:-TieredCompilation -XX:+UseParallelGC -jar Lab2.jar

# Показать все флаги JIT
java -XX:+PrintFlagsFinal -version | grep -i compile
```
