# Лабораторная работа №2: JIT — интерпретация, C1, C2

## Зачем это нужно

В первой лабораторной вы увидели, что Kotlin превращается в байт-код. Но байт-код — это ещё не то, что выполняется на процессоре. JVM может делать с ним две принципиально разные вещи:

- **интерпретировать** — читать инструкцию за инструкцией и выполнять;
- **компилировать** — превращать горячие методы в машинный код, который процессор выполняет напрямую.

Один и тот же `.class` может работать в десятки раз быстрее или медленнее — в зависимости от того, что JVM решила сделать с вашим кодом. Эта лабораторная — про то, чтобы **увидеть этот механизм своими глазами** и перестать верить в магию «JVM сама всё оптимизирует».

Без этого невозможно:

- понимать, почему код на JVM греется и только потом становится быстрым;
- объяснять, почему «одинаковый» код на Java и C++ даёт разную скорость;
- читать логи JIT и понимать, что именно оптимизировалось;
- отвечать на собеседованиях про JIT, tiered compilation и OSR.

Это прямой мост от первой лабораторной к железу: байт-код → JIT → машинный код → процессор.

## Немного теории перед экспериментами

**Что делает JVM с методом:**

1. Сначала метод **интерпретируется**.
2. JVM считает, сколько раз он вызывался и сколько итераций цикла прошло.
3. Когда счётчик превышает порог — метод попадает в очередь на компиляцию.
4. **C1 (client compiler)** — быстрая компиляция, лёгкие оптимизации.
5. **C2 (server compiler)** — медленная, но агрессивная оптимизация. Включается для «горячих» методов.
6. Иногда C2 ошибается в предположениях — тогда происходит **деоптимизация**, и метод возвращается к интерпретации или C1.

**Уровни компиляции (tiered compilation, по умолчанию включена):**

| Уровень | Что это |
|---|---|
| 0 | Интерпретация |
| 1 | C1 без профилирования |
| 2 | C1 с лёгким профилированием |
| 3 | C1 с полным профилированием |
| 4 | C2 |

Метод может «подниматься» и «опускаться» по этим уровням.

**Что такое OSR:**
Если метод вызывается один раз, но внутри него — длинный цикл, JIT не ждёт завершения метода. Он компилирует **тело цикла прямо во время его выполнения** и заменяет интерпретируемый кадр на стеке скомпилированным. Это называется **On-Stack Replacement**. В выводе `PrintCompilation` такие компиляции помечаются знаком `%`.

## Эксперименты

### Эксперимент 1. Один код — разная скорость

```kotlin
fun sumArray(arr: IntArray): Long {
    var s = 0L
    for (x in arr) s += x
    return s
}

fun main() {
    val arr = IntArray(10_000_000) { it }
    var total = 0L
    repeat(10) {
        val t = System.nanoTime()
        total += sumArray(arr)
        val ms = (System.nanoTime() - t) / 1_000_000.0
        println("run $it: $ms ms")
    }
    println("total = $total")
}
```

**Задача:**
1. Запустить обычным способом. Записать времена всех 10 прогонов.
2. Запустить с `-Xint`. Записать.
3. Запустить с `-Xcomp`. Записать.
4. Построить таблицу: режим → первый прогон → последний прогон → во сколько раз быстрее.

**Вопросы:**
- Почему в обычном режиме первый прогон медленный, а последующие быстрые?
- Почему `-Xint` стабильно медленный?
- Почему `-Xcomp` может быть быстрее `-Xint`, но медленнее обычного режима на старте?

**Для отчёта:** таблица «режим → время 1-го прогона → время 10-го прогона → ускорение».

### Эксперимент 2. Кто и когда компилируется

```kotlin
fun hot(n: Int): Long {
    var s = 0L
    for (i in 0 until n) s += i
    return s
}

fun cold(n: Int): Long {
    return n.toLong() * 2
}

fun main() {
    repeat(200_000) { hot(100) }
    println(cold(5))
}
```

**Задача:**
1. Запустить с `-XX:+PrintCompilation`.
2. Найти в выводе строки про `hot` и `cold`.
3. Расшифровать формат строки. Пример:
   ```
   123   45       3       MainKt::hot (15 bytes)
   ```
   - первое число — время от старта JVM в мс;
   - второе — номер компиляции по порядку;
   - третье — уровень (1–4);
   - `%` — значит, компиляция «на стеке» (OSR);
   - `!` — метод с исключениями;
   - `s` — synchronized;
   - `made not entrant` — JVM отбросила старую версию метода;
   - `uncommon trap` — деоптимизация.

**Вопросы:**
- Какой метод скомпилировался? Какой нет? Почему?
- Что такое OSR и почему он появляется?
- Сколько времени прошло до первой компиляции?
- Что означает `made not entrant` и `uncommon trap`, если они есть в выводе?

**Дополнительно:**
- Уменьшите `repeat` до 100 и посмотрите, компилируется ли `hot` вообще.
- Замените `hot` на `cold` внутри `repeat` и убедитесь, что роли меняются.
- Запустите с `-XX:-TieredCompilation` и посмотрите, как меняется картина.
