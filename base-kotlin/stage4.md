## Техническое задание: Сквозной проект (Спринты 1–4)
## Разработка комплексного консольного движка Pokémon TCG
------------------------------
## 1. Контекст и архитектурная цель
Сквозной проект представляет собой поэтапную сборку базового движка для моделирования игровой сессии Pokémon TCG. Проект объединяет четыре последовательных этапа разработки (Спринта):

1. Спринт № 1: Оцифровка структуры данных карты Тренера.
2. Спринт № 2: Моделирование состояния игрового стола, работа с динамическими счетчиками ресурсов и кастинг типов.
3. Спринт № 3: Реализация движка правил, условных проверок (if-else, when) и вычисление базового статуса боя.
4. Спринт № 4: Интеграция циклических конструкций (while, do-while, for) для пошагового поиска карт, симуляции бросков монетки и проведения серийных атак.

Итоговая программа представляет собой единый исполняемый пайплайн (Main.kt), выполняющий пошаговую обработку пользовательского ввода, валидацию ресурсов, расчет урона с учетом элементальной уязвимости, случайных факторов и формирование итогового консольного отчета.
------------------------------
## 2. Спецификация данных (Data Model)## 2.1. Входные текстовые параметры (Считываются через readln())

* Свойства карты (Спринт № 1): cardTypeInput, cardSubtypeInput, cardNameInput, effectTextInput, ruleTextInput, illustratorInput.
* Параметры состояния и боя (Спринты № 2–3):
* deckSizeInput (String) — начальный размер колоды.
    * energyOnBoardInput (String) — доступный запас энергии на столе.
    * discardEnergyCostInput (String) — стоимость сброса энергии для атаки.
    * baseDamageInput (String) — базовый урон атаки.
    * attackerElementInput (String) — стихия атакующего Покемона ("Fire", "Water", "Grass").
    * defenderElementInput (String) — стихия защищающегося Покемона ("Fire", "Water", "Grass").
    * defenderHpInput (String) — текущее HP противника до атаки.
* Параметры управления циклами (Спринт № 4):
* searchDepthInput (String) — глубина просмотра колоды пользователем для поиска карты стадиона.
    * coinResultInput (String) — ввод стороны монетки пользователем ("Heads" — Орел, "Tails" — Решка).
    * attackStrikesInput (String) — количество ударов, которое заявляет игрок для серийной атаки.

## 2.2. Приведенные числовые параметры и свойства

* healAmount (Int = 60), cardNumber (Int = 105), totalInSet (Int = 106) — характеристики карты (Спринт № 1).
* deckSize (Int) — deckSizeInput.toInt().
* energyOnBoard (Int) — energyOnBoardInput.toInt().
* discardEnergyCost (Int) — discardEnergyCostInput.toInt().
* baseDamage (Int) — baseDamageInput.toInt().
* defenderHp (Int, var) — defenderHpInput.toInt() (становится изменяемой переменной в Спринте № 4).
* searchDepth (Int) — searchDepthInput.toInt().
* attackStrikes (Int) — attackStrikesInput.toInt().

## 2.3. Динамические переменные состояния и вычисляемые показатели

* cardsInHand (Int, var) — количество карт в руке (начальное значение: 7).
* discardPileSize (Int, var) — количество карт в сбросе (начальное значение: 0).
* isAttackAllowed (Boolean, var) — флаг валидации достаточности энергии.
* stadiumFound (Boolean = false, var) — флаг успешного нахождения карты Стадиона (Спринт № 4).
* headsCount (Int, var) — счетчик выпавших подряд «Орлов» для усиления атаки (Спринт № 4, изначально 0).
* weaknessMultiplier (Double, val) — коэффициент уязвимости по стихиям (1.0, 1.2, 1.5, 2.0).
* finalDamage (Double, val) — урон одного стандартного попадания (baseDamage * weaknessMultiplier).
* remainingHp (Int, var) — остаток HP противника после всей серии атак (не менее 0).
* matchStatus (String, var) — вердикт по состоянию противника после атаки.

## 3. Требования к алгоритму и логике работы
Программа Main.kt должна выполнять следующую цепочку действий:
## Блок 1. Оцифровка карты и инициализация (Спринт № 1)

1. Запросить у пользователя с помощью print() текстовые характеристики карты Тренера.
2. Инициализировать константы healAmount (60), cardNumber (105), totalInSet (106).
3. Форматированно вывести карточку в консоль согласно эталонному макету (со сплошными разделителями и интерполяцией строк $).

## Блок 2. Считывание параметров стола и манипуляция счетчиками (Спринт № 2)

1. Запросить deckSizeInput и energyOnBoardInput, привести к Int с помощью .toInt().
2. Промоделируйте розыгрыш карты предмета: декрементировать cardsInHand-- и инкрементировать discardPileSize++.

## Блок 3. Поиск карт и симуляция монетки (Спринт № 4 — Циклы while и do-while)

1. Циклический поиск карты Стадиона (Цикл while с оператором break):
* Запросить у пользователя глубину просмотра колоды: print("На сколько карт вглубь колоды вы готовы провести поиск стадиона? "). Привести ввод к числу searchDepth.
    * Запустить цикл while, который выполняется, пока счетчик просмотренных карт currentCard (начиная с 1) не превысит searchDepth.
    * На каждой итерации выводить лог: "[ПОИСК] Проверяется карта №$currentCard...".
    * Условие успешного поиска: Карта Стадиона лежит в колоде под номером 4. Если currentCard == 4, установить stadiumFound = true, вывести лог "[УСПЕХ] Карта Стадиона найдена и выложена на стол!" и прервать цикл с помощью оператора break.
    * Если карта не равна 4, инкрементировать счетчик currentCard++.
2. Симуляция бросков монетки для супер-удара (Цикл do-while):
* Игрок кидает монетку до тех пор, пока не выпадет «Решка» ("Tails"). Каждый выпавший «Орел» ("Heads") увеличивает счетчик силы удара.
    * Используйте цикл do-while, чтобы гарантировать минимум один бросок монетки.
    * Внутри цикла запросить ввод: print("Подбросьте монетку! Что выпало? (Heads/Tails): "). Считать строку coinResultInput.
    * Если введено "Heads", увеличить счетчик headsCount++ и вывести лог: "[МОНЕТКА] Отлично! Дополнительный урон зафиксирован.".
    * Условие продолжения цикла while (...): продолжать броски, пока пользователь вводит "Heads". Как только вводится "Tails", цикл завершается.

## Блок 4. Проверка правил и ввод параметров боя (Спринт № 2–3)

1. Запросить discardEnergyCostInput, привести к Int и прибавить к сбросу с помощью составного присваивания discardPileSize += discardEnergyCost.
2. Валидация ресурсов (Классический if-else):
* Если energyOnBoard >= discardEnergyCost — установить isAttackAllowed = true и вывести лог успешной проверки.
    * Иначе — установить isAttackAllowed = false, вывести сообщение об ошибке и завершить выполнение атаки.
3. Ввод параметров боя: При успешной валидации запросить baseDamageInput, attackerElementInput, defenderElementInput, defenderHpInput и кастить числовые значения.
4. Расчет уязвимости (when Expression с блоками { }):
* "Water" против "Fire" $\rightarrow$ вывод лога эффекта, возврат 2.0.
    * "Fire" против "Grass" $\rightarrow$ вывод лога эффекта, возврат 1.5.
    * "Grass" против "Water" $\rightarrow$ вывод лога эффекта, возврат 1.2.
    * Во всех остальных случаях $\rightarrow$ вывод лога базового урона, возврат 1.0.
    * Рассчитать finalDamage = baseDamage * weaknessMultiplier.

## Блок 5. Серийная атака и завершение хода (Спринт № 4 — Цикл for)

1. Серийная атака «Яростные удары» (Цикл for с break и continue):
* Запросить у пользователя количество планируемых ударов: print("Сколько ударов совершает атака 'Яростные удары'? "). Привести к числу attackStrikes.
    * Организовать цикл for по диапазону 1..attackStrikes, где переменная итерации называется strike.
    * Внутри цикла на каждом ударе:
    * Проверка на критический промах (continue): Каждый 3-й удар (strike % 3 == 0) всегда приходится мимо цели из-за усталости Покемона. Вывести сообщение: "Удар №$strike: [ПРОМАХ] Покемон потерял равновесие. Удар прошел мимо!" и применить оператор continue, чтобы пропустить фазу нанесения урона.
        * Нанесение урона: В случае попадания к finalDamage прибавить бонус за монетки (headsCount * 10). Уменьшить здоровье противника: defenderHp -= (finalDamage + headsCount * 10).
        * Вывести лог удара: "Удар №$strike: Нанесено ${finalDamage + headsCount * 10} урона. У противника осталось $defenderHp HP.".
        * Проверка на завершение боя (break): Если defenderHp опустилось до 0 или ниже, вывести сообщение: "Покемон противника полностью повержен на ударе №$strike!" и немедленно остановите цикл с помощью оператора break.
    2. Завершение хода:
* Вычислить остаток HP с защитой от отрицательных значений через выражение if-else: remainingHp = if (defenderHp < 0) 0 else defenderHp.
    * Промоделировать конец хода: декрементировать колоду deckSize--, инкрементировать руку cardsInHand++ и вычислить остаток от деления deckSize % 2.

## Блок 6. Определение статуса боя (Безаргументное выражение when)

* remainingHp == 0 $\rightarrow$ "ПОКЕМОН НОКАУТИРОВАН! Возьмите призовую карту (Prize Card).".
* remainingHp in 1..30 $\rightarrow$ "КРИТИЧЕСКОЕ СОСТОЯНИЕ! Противник на грани нокаута.".
* Иначе $\rightarrow$ "БОЙ ПРОДОЛЖАЕТСЯ. Противник сохраняет боеспособность.".

## 5. Критерии оценки (3-балльная шкала)## Оценка «5» (Отлично)

* Все 4 модуля сквозного проекта успешно интегрированы в единый рабочий файл Main.kt без синтаксических ошибок.
* Цикл while осуществляет контролируемый пошаговый поиск и досрочно завершается через break строго на 4-й позиции.
* Конструкция do-while корректно обрабатывает поочередный ввод бросков монетки, выполняясь минимум один раз и останавливаясь ровно на значении "Tails".
* Боевой цикл for работает по динамически вводимому диапазону 1..attackStrikes.
* Оператор continue корректно изолирован внутри условия strike % 3 == 0 и не ломает нанесение урона в штатных раундах.
* Оператор break в цикле for мгновенно останавливает выполнение программы при обнулении HP противника.
* Все выводы и переменные состояния стола консистентны и обновляются без потерь из предыдущих модулей.

## Оценка «4» (Хорошо)

* Программа полностью компилируется и работает, но логика циклов имеет недочеты.
* Присутствуют отклонения: например, вместо цикла do-while для монетки использован обычный while с искусственной инициализацией переменной, или перепутана логика пропуска ходов (пропускаются не те удары в цикле for).

## Оценка «3» (Удовлетворительно)

* Программа запускается, но циклы приводят к зависанию (бесконечный цикл while или do-while из-за отсутствия изменения проверяемых переменных/условий).
* Нарушена связность между модулями, или часть логики зашита константами в теле циклов.
