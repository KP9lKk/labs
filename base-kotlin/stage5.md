# Техническое задание: Сквозной проект (Спринты 1–4)

## Разработка комплексного консольного движка Pokémon TCG

---

### 1. Контекст и архитектурная цель

Сквозной проект представляет собой поэтапную сборку базового движка для моделирования игровой сессии **Pokémon TCG**. Проект объединяет четыре последовательных этапа разработки (Спринта):

1. **Спринт № 1:** Оцифровка структуры данных карты Тренера.

2. **Спринт № 2:** Моделирование состояния игрового стола, работа с динамическими счетчиками ресурсов и кастинг типов.

3. **Спринт № 3:** Реализация движка правил, условных проверок (`if-else`, `when`) и вычисление статуса боя.

4. **Спринт № 4:** Переход от числовых счетчиков к полноценным структурам данных — коллекциям (`MutableList`, `Map`), функциональным операциям (`filter`, `map`, `sortedBy`, `joinToString`) и анализу содержимого игровых зон.

Ключевая задача Спринта № 4 — **обратная совместимость**: вместо «просто чисел» (`cardsInHand`, `discardPileSize`, `deckSize`) программа теперь оперирует реальными списками карт, а числовые показатели вычисляются через свойство `.size`. Сценарий боя (валидация энергии, расчет уязвимости, статус) наследуется из Спринта № 3 без изменений логики.

Итоговая программа представляет собой единый исполняемый пайплайн (`Main.kt`), выполняющий пошаговую обработку пользовательского ввода, ведение игровых зон на базе коллекций, расчет урона с учетом элементальной уязвимости и формирование расширенного консольного отчета с аналитикой по колоде, руке и сбросу.

### 2. Спецификация данных (Data Model)

#### **2.1. Входные текстовые параметры (Считываются через `readln()`)**

* **Свойства карты (Спринт № 1):** `cardTypeInput`, `cardSubtypeInput`, `cardNameInput`, `effectTextInput`, `ruleTextInput`, `illustratorInput` — без изменений относительно Спринта № 1.

* **Параметры состояния и боя (Спринты № 2–4):**
* `deckSeedInput` (`String`) — список стартовых карт колоды, введенных через запятую (например, `"Pikachu, Potion, Switch, Fire Energy"`).

* `energyOnBoardInput` (`String`) — доступный запас энергии на столе.
* `discardEnergyCostInput` (`String`) — стоимость сброса энергии для атаки.

* `playedCardInput` (`String`) — название карты предмета, разыгрываемой из руки.

* `energyCardsInput` (`String`) — список сбрасываемых карт энергии через запятую (например, `"Fire Energy, Water Energy"`).
* `baseDamageInput` (`String`) — базовый урон атаки.
* `attackerElementInput` (`String`) — стихия атакующего Покемона (`"Fire"`, `"Water"`, `"Grass"`).
* `defenderElementInput` (`String`) — стихия защищающегося Покемона (`"Fire"`, `"Water"`, `"Grass"`).
* `drawCountInput` (`String`) — количество карт добора в конце хода.

#### **2.2. Приведенные числовые параметры и свойства**

* `healAmount` (`Int = 60`), `cardNumber` (`Int = 105`), `totalInSet` (`Int = 106`) — характеристики карты (Спринт № 1).

* `energyOnBoard` (`Int`) — `energyOnBoardInput.toInt()`.
* `discardEnergyCost` (`Int`) — `discardEnergyCostInput.toInt()`.

* `baseDamage` (`Int`) — `baseDamageInput.toInt()`.
* `drawCount` (`Int`) — `drawCountInput.toInt()`.

#### **2.3. Коллекции игрового состояния (новое в Спринте № 4)**

* `deck` (`MutableList<String>`) — колода. Инициализируется разбором `deckSeedInput` через `.split(", ")` и `.toMutableList()`.
* `hand` (`MutableList<String>`) — рука игрока. Начальное значение: `mutableListOf("Pikachu", "Potion", "Fire Energy", "Switch", "Professor's Research", "Water Energy", "Charmander")` (7 карт).

* `discardPile` (`MutableList<String>`) — сброс. Начальное значение: пустой список.
* `boardSummary` (`Map<String, Int>`) — словарь сводки стола вида `"Колода" to deck.size`, `"Рука" to hand.size`, `"Сброс" to discardPile.size` (пересобирается перед итоговым отчетом).

* `discardedEnergyCards` (`List<String>`) — результат разбора `energyCardsInput` через `.split(", ")`.

#### **2.4. Вычисляемые показатели и динамические флаги**

* `isAttackAllowed` (`Boolean`, `var`) — флаг валидации достаточности энергии (наследуется из Спринта № 3).

* `wasCardPlayed` (`Boolean`, `val`) — результат `hand.remove(playedCardInput)`; используется для проверки, что карта действительно была в руке.
* `weaknessMultiplier` (`Double`, `val`) — коэффициент уязвимости по стихиям (`1.0`, `1.2`, `1.5`, `2.0`) — логика Спринта № 3.

* `finalDamage` (`Double`, `val`) — итоговый урон (`baseDamage * weaknessMultiplier`).
* `remainingHp` (`Int`, `val`) — остаток HP противника после атаки (не менее `0`).
* `matchStatus` (`String`, `val`) — вердикт по состоянию противника (безаргументный `when` из Спринта № 3).

* `energyTypeCount` (`Int`, `val`) — количество карт типа `"Energy"` в сбросе, вычисленное через `discardPile.count { it.endsWith("Energy") }`.
* `sortedDiscard` (`List<String>`, `val`) — сброс, отсортированный по алфавиту через `sortedBy { it }`.

### 3. Требования к алгоритму и логике работы

Программа `Main.kt` должна выполнять следующую цепочку действий:

#### **Блок 1. Оцифровка карты и инициализация (Спринт № 1 — без изменений)**

1. Запросить у пользователя с помощью `print()` текстовые характеристики карты Тренера.

2. Инициализировать константы `healAmount` (60), `cardNumber` (105), `totalInSet` (106).
3. Форматированно вывести карточку в консоль согласно эталонному макету (со сплошными разделителями и интерполяцией строк `$`).

#### **Блок 2. Инициализация игровых зон через коллекции (Спринт № 4)**

1. Запросить `deckSeedInput` и развернуть строку в колоду: `val deck = deckSeedInput.split(", ").toMutableList()`.

2. Инициализировать `hand` (7 стартовых карт) и пустой `discardPile`.
3. Вывести сводку зон циклом `for ((zone, count) in boardSummary)`, где `boardSummary` собран через `mapOf("Колода" to deck.size, ...)` — числовые счетчики Спринта № 2 теперь вычисляются из `.size` коллекций.

#### **Блок 3. Манипуляция зонами через методы `MutableList` (Спринты № 2 + № 4)**

1. Запросить `energyOnBoardInput`, привести к `Int`.

2. Запросить `playedCardInput` и промоделировать розыгрыш карты предмета:
* Выполнить `val wasCardPlayed = hand.remove(playedCardInput)` — карта удаляется из руки **только если она там есть**.

* Через `if-else` (выражение Спринта № 3): при `wasCardPlayed == true` добавить карту в сброс `discardPile.add(playedCardInput)` и вывести лог; иначе вывести предупреждение, что карта не найдена в руке.

3. Запросить `discardEnergyCostInput`, привести к `Int`.
4. Запросить `energyCardsInput`, развернуть в `discardedEnergyCards` и в цикле добавить каждую карту в `discardPile` через `forEach { discardPile.add(it) }`.

#### **Блок 4. Проверка правил, расчет урона и состояния (Спринт № 3 — без изменений логики)**

1. **Валидация ресурсов (классический `if-else`):**
* Если `energyOnBoard >= discardEnergyCost` — установить `isAttackAllowed = true` и вывести лог успешной проверки.

* Иначе — установить `isAttackAllowed = false`, вывести сообщение об ошибке и завершить выполнение атаки.

2. **Ввод параметров боя:** при успешной валидации запросить `baseDamageInput`, `attackerElementInput`, `defenderElementInput`, `defenderHpInput`.

3. **Расчет уязвимости (`when`-выражение с блоками `{ }`):** та же матрица множителей, что и в Спринте № 3 (`Water` vs `Fire` → `2.0`; `Fire` vs `Grass` → `1.5`; `Grass` vs `Water` → `1.2`; иначе → `1.0`).

4. **Математический расчет:** `finalDamage = baseDamage * weaknessMultiplier`, остаток HP с защитой от отрицательных значений.

#### **Блок 5. Конец хода и добор карт (Спринт № 4)**

1. Запросить `drawCountInput`, привести к `Int`.

2. Промоделировать добор: цикл `repeat(drawCount) { ... }` — на каждой итерации проверить `deck.isNotEmpty()`; если колода не пуста, извлечь верхнюю карту методом `deck.removeAt(deck.lastIndex)` и добавить её в руку `hand.add(...)`; иначе вывести предупреждение «Колода пуста!».

3. Вычислить аналитику сброса через функциональные операции:
* `energyTypeCount = discardPile.count { it.endsWith("Energy") }`.

* `sortedDiscard = discardPile.sortedBy { it }`.

#### **Блок 6. Итоговый отчет с аналитикой коллекций (Спринты № 2–4)**

1. Пересобрать `boardSummary` (`mapOf` по `.size` всех зон).

2. Вывести сводный консольный лог:
* Результат проверки атаки, типы, расчетный урон, остаток HP и статус (наследуется из Спринта № 3).
* Остаток энергии, содержимое руки через `hand.joinToString(", ")`.

* Отсортированное содержимое сброса через `sortedDiscard.joinToString(", ")` с разбивкой по типу (`энергия: N шт.` / `прочие: M шт.`).
* Сводку зон циклом `for ((zone, count) in boardSummary)` и остаток колоды с четностью `deck.size % 2`.

### 5. Критерии оценки (3-балльная шкала)

#### **Оценка «5» (Отлично)**

* Все 4 модуля сквозного проекта интегрированы в единую рабочую программу без синтаксических ошибок.
* Игровые зоны (колода, рука, сброс) реализованы как `MutableList<String>`; ввод колоды разбирается через `.split(", ").toMutableList()`.

* Перемещение карт между зонами выполнено методами `add` / `remove` / `removeAt`, результат `remove()` (Boolean) проверяется через `if-else`.

* Числовые счетчики отчета вычисляются из `.size` коллекций, а не хранятся отдельными переменными (как в Спринтах № 2–3).
* Добор из колоды защищен проверкой `deck.isNotEmpty()` — программа не падает на пустой колоде.

* Аналитика сброса построена на функциональных операциях: `count { }`, `sortedBy { }`, `joinToString`.
* Логика Спринтов № 1–3 (карта, валидация, `when`-выражения, статус боя) сохранена без искажений.
* Вывод полностью структурирован и отформатирован шаблонами строк `$`.

#### **Оценка «4» (Хорошо)**

* Код компилируется и правильно выполняет сценарий.
* Присутствуют недочеты:
* Счетчики (`cardsInHand`, `discardPileSize`) ведутся отдельными числовыми переменными параллельно со списками, а не вычисляются через `.size`.

* Добор реализован через `deck.removeAt(0)` без защиты от пустой колоды.
* Вместо `count { }` / `sortedBy { }` применен ручной перебор в цикле `for`.
* Нарушено форматирование итогового отчета относительно эталонного макета.

#### **Оценка «3» (Удовлетворительно)**

* Программа запускается, но логика нарушена:
* Попытка изменять read-only `List` (`listOf`) вместо `MutableList`.

* Игнорируется результат `remove()` — карта «сбрасывается», даже если её не было в руке.
* Коллекции не связаны между модулями: зоны пересоздаются заново в каждом блоке.
* Доступ по индексу выходит за границы (`IndexOutOfBoundsException`) при исчерпании колоды.

#### **Оценка «2» / Не зачтено**

* Программа не компилируется или студент не может объяснить отличие `List` от `MutableList` и то, как операции `filter` / `count` / `sortedBy` работают с коллекциями игровых зон.
