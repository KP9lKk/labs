# Техническое задание: Декомпозиция игрового движка Pokémon TCG и архитектура методов

## 1. Контекст и связь с предыдущими частями
В рамках данной лабораторной работы производится глобальный **рефакторинг и декомпозиция** кода турнирного цикла, созданного на предыдущем этапе:
1. **Часть 2 и Часть 4:** Логика расчёта входящего урона с учётом типов (уязвимостей/устойчивостей) выносится из тела `Main` в изолированный функциональный блок.
2. **Часть 4 (Менеджмент ресурсов):** Логика лечения активного покемона и менеджмента инвентаря тренера обособляется в отдельный защищённый подмодуль.
3. **Система логирования раундов:** Вместо разрозненных вызовов `Console.WriteLine` внедряется централизованная подсистема гибкого вывода игровых событий.

**Главная цель рефакторинга:** Полностью отказаться от громоздкого линейного кода внутри метода `Main`. Программа разделяется на изолированные статические методы (функции), каждый из которых отвечает за строго одну задачу, безопасно оперирует памятью и использует современные модификаторы параметров (`ref`, `out`, `in`, `params`).

## 2. Архитектура методов и технические требования

### 2.1. Метод «Боевой калькулятор урона» (Возвращающие методы и `in`)
* **Имя метода:** `CalculateIncomingDamage`
* **Тип возвращаемого значения:** `int` (итоговый нанесенный урон)
* **Входные параметры:**
  * `in int baseDamage` — базовый урон противника (доступ только для чтения).
  * `in int attackType` — числовой идентификатор модификатора типа (`1` — Уязвимость, `2` — Устойчивость, `3` — Обычный).
* **Логика работы:** 
  Внутри метода реализуется конструкция `switch` по параметру `attackType`:
  * Если тип равен `1` (Уязвимость): базовый урон удваивается.
  * Если тип равен `2` (Устойчивость): урон снижается на 20 единиц (минимальный урон не может упасть ниже 0).
  * Если тип равен `3` (Обычный): урон возвращается без изменений.
* **Защита данных:** В коде метода должна быть предпринята попытка перезаписать значение переменной `baseDamage` (например, `baseDamage = 10;`). Студент обязан зафиксировать ошибку компиляции C#, удалить/закомментировать строку и оставить текстовое пояснение причины ошибки.

### 2.2. Метод «Фаза применения предметов» (Использование `ref` и `out`)
* **Имя метода:** `UseItem`
* **Тип возвращаемого значения:** `void`
* **Входные и выходные параметры:**
  * `ref int pokemonHP` — текущее здоровье активного бойца (передаётся по ссылке для прямой модификации внешней переменной).
  * `List<string> bag` — динамическая коллекция (инвентарь игрока).
  * `out int itemsLeft` — выходной параметр для возврата оставшегося числа предметов в вызывающий код.
* **Логика работы:**
  1. Метод проверяет наличие строки `"Зелье HP"` внутри списка `bag`.
  2. Если предмет найден: `pokemonHP` увеличивается на +30 единиц, а сам предмет удаляется из инвентаря через встроенный метод `.Remove()`.
  3. Если предмета нет: на консоль выводится уведомление: `"Лечение невозможно!"`.
  4. Перед завершением метода в `itemsLeft` **обязательно** записывается актуальное значение `bag.Count`.

### 2.3. Метод «Логирование событий раунда» (Использование `params`)
* **Имя метода:** `LogRoundEvents`
* **Тип возвращаемого значения:** `void`
* **Входные параметры:**
  * `params string[] events` — массив текстовых строк переменной длины.
* **Логика работы:**
  Метод генерирует визуальную рамку лога. При помощи цикла `foreach` происходит итерация по всем переданным аргументам. Каждая строка выводится на экран с обязательным префиксом `"[БОЙ]: "`.

## 3. Интеграция в глобальный игровой цикл (`Main`)

1. **Регистрация и инициализация:** Сохраняется механика заполнения массивов команды и списка инвентаря тренера из Stage 4.
2. **Интеграция `UseItem`:** При выборе игроком действия «Сумка» (меню, пункт 2) программа вызывает метод `UseItem`, передавая туда здоровье текущего покемона по ссылке (`ref`), инвентарь и переменную под остаток вещей (`out`).
3. **Интеграция `CalculateIncomingDamage`:** В фазе контратаки компьютера расчет финального урона по игроку полностью делегируется созданному калькулятору. Полученное из метода `int` значение вычитается из здоровья покемона.
4. **Интеграция `LogRoundEvents`:** В самом конце каждого раунда вызывается метод логирования. В него в виде перечисления строк через запятую передаются динамические данные раунда (какая атака применена, был ли крит, сколько урона получено).

## 4. Эталонный формат консольного вывода подмодулей

### Тест модуля 1 (Боевой калькулятор урона)
```text
=== БОЕВОЙ КАЛЬКУЛЯТОР ===
Базовый урон противника: 25
Тип атаки (1 - Боевой, 2 - Стальной, 3 - Обычный): 1
[Калькулятор] Расчёт: Боевой тип! Урон удваивается.
Итоговый нанесенный урон: 50
```

```text
=== СИСТЕМА ИНВЕНТАРЯ ===
Здоровье до лечения: 25 HP.
[Предмет] Использовано: Зелье HP. Здоровье восстановлено на +30!
Осталось предметов в сумке: 2
Здоровье после лечения: 55 HP.
```

### Тест модуля 3 (Динамическое логирование)
```text
--- ЛОГ ТЕКУЩЕГО РАУНДА ---
[БОЙ]: Пикачу использует Быстрая Атака!
[БОЙ]: Выпал орёл! Нанесен критический урон.
[БОЙ]: Враг Булбазавр потерял 30 HP.
--------------------------
```

## 5. Критерии оценки (По системе Stage 4)

* **Оценка «5» (Отлично):** Код полностью декомпозирован. В `Main` отсутствует прямая математика боя и ручной вывод логов. Модификаторы `in`, `ref`, `out` и `params` применены строго по назначению без ошибок компиляции. Передача аргументов в `params` идет списком через запятую.
* **Оценка «4» (Хорошо):** Программа работает, но допущены архитектурные отступления: параметры `in` проигнорированы, вместо `out` используется стандартный `return`, либо массив для `params` создается и передается вручную.
* **Оценка «3» (Удовлетворительно):** Корректно обособлен только один из методов (например, калькулятор урона), либо при работе со ссылочными модификаторами (`ref`/`out`) возникают критические ошибки, приводящие к падению игрового цикла.
