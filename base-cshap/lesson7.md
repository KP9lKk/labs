## Тема: Наследование и полиморфизм в C#. Абстрактные классы, виртуальные методы и интерфейсы

## 1. Краткие теоретические сведения

### 1.1. Зачем вообще наследование?
В прошлой лабораторной у нас был один класс `Pokemon`. Но представь: у тебя 150 покемонов, и каждый атакует по-своему. Писать 150 отдельных классов с нуля — это боль. Наследование позволяет вынести общее в базовый класс, а различия — в наследников.

Если `Pikachu`, `Squirtle` и `Charmander` — это всё покемоны, значит, у них есть общее: имя, уровень, HP, метод `ShowInfo()`. Это и есть базовый класс `Pokemon`. А вот атака у каждого своя — это уже дело наследников.

```csharp
class Pokemon          // базовый класс
{
    public string Name;
    public int Level;
}

class Pikachu : Pokemon  // наследник
{
    public void ThunderShock() { ... }
}
```

Двоеточие `:` читается как «наследуется от» или «является». `Pikachu` **является** `Pokemon`.

### 1.2. `base` — обращение к родителю
Если у базового класса есть конструктор с параметрами, наследник обязан его вызвать через `base(...)`:

```csharp
class Pokemon
{
    public string Name;
    public int Level;

    public Pokemon(string name, int level)
    {
        Name = name;
        Level = level;
    }
}

class Pikachu : Pokemon
{
    public Pikachu(string name, int level) : base(name, level)
    {
        // тут можно добавить что-то своё
    }
}
```

`base(...)` вызывается **до** тела конструктора наследника. Это как сначала «родиться покемоном», а потом «стать именно Пикачу».

### 1.3. `virtual` и `override` — полиморфизм в действии
Метод базового класса можно пометить `virtual` — это значит «наследники могут переопределить меня». Наследник использует `override`, чтобы дать свою версию.

```csharp
class Pokemon
{
    public virtual void Attack()
    {
        Console.WriteLine($"{Name} атакует как-то непонятно.");
    }
}

class Pikachu : Pokemon
{
    public override void Attack()
    {
        Console.WriteLine($"{Name} бьёт током! Пика-пика!");
    }
}

class Squirtle : Pokemon
{
    public override void Attack()
    {
        Console.WriteLine($"{Name} стреляет водой! Сквирт-сквирт!");
    }
}
```

Теперь если у тебя есть переменная типа `Pokemon`, в которую положен `Pikachu`, вызов `Attack()` приведёт к версии Пикачу. Это и есть **полиморфизм**: один вызов — разное поведение.

```csharp
Pokemon p = new Pikachu("Пикачу", 5);
p.Attack(); // Выведет: Пикачу бьёт током!
```

### 1.4. Абстрактные классы: «нельзя создать просто покемона»
Иногда базовый класс — это настолько общее понятие, что его экземпляр не имеет смысла. Что такое «просто покемон»? Это абстракция. В C# для этого есть `abstract`:

```csharp
abstract class Pokemon
{
    public string Name;
    public abstract void Attack(); // нет тела, наследник ОБЯЗАН реализовать
}
```

Особенности:
- Нельзя сделать `new Pokemon(...)` — компилятор не даст.
- Абстрактный метод **обязан** быть переопределён в наследнике.
- В абстрактном классе могут быть и обычные методы, и поля, и конструкторы.

### 1.5. `protected`: доступ для наследников
`private` — видно только внутри класса. `public` — видно всем. `protected` — видно классу и его наследникам, но не посторонним. Идеально для полей, которые должны быть доступны детям, но не всему миру.

```csharp
abstract class Pokemon
{
    protected int hp;   // доступно наследникам
    public int HP => hp; // публичное свойство для всех
}
```

### 1.6. Интерфейсы: контракт без родства
Иногда нужно сказать «этот объект умеет вот это», не делая его чьим-то родственником. Например, покемон может уметь плавать, летать, эволюционировать. Это не «является», это «умеет». Для этого — интерфейсы.

```csharp
interface IEvolvable
{
    void Evolve();
}

class Charmander : Pokemon, IEvolvable
{
    public void Evolve()
    {
        Console.WriteLine($"{Name} эволюционирует в Чармелеона!");
    }
}
```

Класс может наследоваться только от одного класса, но реализовывать **сколько угодно интерфейсов**.

### 1.7. Шпаргалка: когда что использовать?

Это, пожалуй, самый частый вопрос на собеседованиях и на защите. Давай разложим по полочкам.

#### Обычный класс (`class`)
**Когда использовать:** когда у сущности есть конкретная реализация, и ты планируешь создавать её экземпляры через `new`.

**Признаки:**
- Ты можешь сказать «вот это — законченная вещь, её можно создать».
- У неё есть состояние (поля) и поведение (методы), которые работают «как есть».
- Наследники возможны, но не обязательны.

**Пример из покемонов:**
```csharp
class Potion   // зелье — конкретная вещь, можно создать
{
    public string Name = "Обычное зелье";
    public int HealAmount = 20;

    public void Use(Pokemon target)
    {
        target.HP += HealAmount;
    }
}
```

Зелье — это не абстракция. Оно существует, его можно купить, использовать. `new Potion()` — валидно.

---

#### Абстрактный класс (`abstract class`)
**Когда использовать:** когда есть общее понятие, которое само по себе не имеет смысла, но задаёт каркас для наследников.

**Признаки:**
- Ты **не можешь** сказать «создай мне просто вот это» — звучит странно.
- Есть общие поля и методы, которые работают одинаково для всех наследников.
- Есть методы, которые каждый наследник обязан реализовать по-своему.
- Наследники — это **разновидности** одного и того же (отношение «является»).

**Пример из покемонов:**
```csharp
abstract class Pokemon   // «просто покемон» — это абстракция
{
    protected string name;
    protected int level;

    public void ShowInfo()  // общее для всех — работает одинаково
    {
        Console.WriteLine($"{name}, ур. {level}");
    }

    public abstract void Attack();  // каждый атакует по-своему
}
```

Ты не можешь создать `new Pokemon(...)`, потому что «просто покемон» — это не конкретный вид. Но `Pikachu`, `Squirtle`, `Charmander` — это уже конкретные виды, и они обязаны реализовать `Attack()`.

**Ключевая фраза-проверка:** «Это **является** чем-то более общим, и у разных видов есть общее состояние».

---

#### Интерфейс (`interface`)
**Когда использовать:** когда нужно описать **способность** или **контракт**, который может быть у совершенно разных, не связанных родством классов.

**Признаки:**
- Ты говоришь не «это является», а «это **умеет**».
- Способность может быть у классов из разных иерархий (покемон умеет летать, но и самолёт умеет летать — общий интерфейс `IFlyable`).
- Нет состояния (полей), только сигнатуры методов, свойств, событий.
- Класс может реализовать **много** интерфейсов одновременно.

**Пример из покемонов:**
```csharp
interface IEvolvable
{
    void Evolve();
}

interface IFlyable
{
    void Fly();
}

class Pidgeotto : Pokemon, IFlyable, IEvolvable
{
    public void Fly()    { Console.WriteLine("Пиджеотто взлетает!"); }
    public void Evolve() { Console.WriteLine("Пиджеотто эволюционирует!"); }
    public override void Attack() { Console.WriteLine("Пиджеотто атакует с воздуха!"); }
}
```

Пиджеотто **является** покемоном (наследование), **умеет** летать и **умеет** эволюционировать (интерфейсы). При этом `Magikarp` — тоже покемон, но летать не умеет. И это нормально.

**Ключевая фраза-проверка:** «Это **умеет** делать вот это, и неважно, кто оно по природе».

---

#### Сводная таблица

| Вопрос | Обычный класс | Абстрактный класс | Интерфейс |
|---|---|---|---|
| Можно создать `new`? | Да | Нет | Нет |
| Есть поля/состояние? | Да | Да | Нет (только свойства-заглушки) |
| Есть реализация методов? | Да | Да (и абстрактные тоже) | Нет (до C# 8; сейчас можно default-реализации, но не увлекайся) |
| Наследоваться можно от скольких? | От одного | От одного | От многих |
| Отношение | — | «Является» | «Умеет» |
| Когда использовать | Конкретная вещь | Общий каркас для родственников | Способность у разных классов |

---

#### Как выбрать за 10 секунд

1. **Могу ли я создать экземпляр и это звучит логично?**
   - Да → обычный класс.
   - Нет → идём дальше.

2. **Это «является» чем-то общим, и у наследников есть общее состояние?**
   - Да → абстрактный класс.
   - Нет → идём дальше.

3. **Это «умеет» что-то, и эту способность могут иметь разные, не связанные классы?**
   - Да → интерфейс.

**Пример-разбор:**
- `Potion` → обычный класс (конкретное зелье).
- `Pokemon` → абстрактный класс (общий каркас, «просто покемона» не существует).
- `IEvolvable`, `IFlyable`, `ISwimmable` → интерфейсы (способности, которые могут быть у разных покемонов).
- `Pikachu` → обычный класс-наследник (конкретный вид, можно создать).

---

#### Частая ошибка новичка
Сделать **всё** интерфейсами, потому что «это гибко». Или сделать **всё** абстрактными классами, потому что «это удобно». На самом деле:

- Интерфейс — это **контракт**, а не хранилище общего кода.
- Абстрактный класс — это **родство**, а не просто «набор методов».
- Обычный класс — это **готовая вещь**, которую можно использовать прямо сейчас.

Если сомневаешься — задай себе вопрос: «Я хочу сказать, что объект **является** чем-то, или что он **умеет** что-то?» Это сразу разведёт абстрактный класс и интерфейс.

## Задание 1. Иерархия покемонов: `virtual` и `override`

**Формулировка задачи:** Создать базовый класс `Pokemon` и несколько наследников, каждый со своей атакой.

### Техническое задание:
1. Создай базовый класс `Pokemon`:
   - поля `protected`: `name`, `level`, `hp`;
   - публичные свойства `Name`, `Level`, `HP` (с проверками, как в прошлой лабораторной);
   - конструктор с параметрами;
   - **виртуальный** метод `Attack()`, который выводит что-то общее (например, «покемон атакует»);
   - обычный метод `ShowInfo()`.
2. Создай **минимум 3 наследника**: `Pikachu`, `Squirtle`, `Charmander` (или свои).
3. Каждый наследник:
   - вызывает `base(...)` в конструкторе;
   - переопределяет `Attack()` через `override` со своей уникальной атакой.
4. В `Main` создай по одному объекту каждого наследника и вызови `Attack()` и `ShowInfo()`.

### Требуемый формат вывода:
```
=== ПОКЕДЕКС: АТАКИ ===
Пикачу (Ур. 5): Пика-пика! Удар током!
Сквиртл (Ур. 7): Сквирт-сквирт! Водяной пистолет!
Чармандер (Ур. 6): Чар-чар! Огненный хвост!
```

**Свобода:** можешь добавить своего покемона (Бульбазавр? Мяут? Гастли?), добавить каждой атаке урон или вероятность промаха. Можешь сделать вывод с рамками или цветом. Главное — базовый класс + минимум 3 наследника с `override`.

## Задание 2. Полиморфизм: один массив — разные покемоны

**Формулировка задачи:** Положить разных покемонов в один массив и вызвать у них метод `Attack()` в цикле. Убедиться, что каждый атакует по-своему — это и есть полиморфизм.

### Техническое задание:
1. Сделай класс `Pokemon` **абстрактным** (`abstract class Pokemon`).
2. Сделай метод `Attack()` **абстрактным** (`public abstract void Attack();`) — без тела. Наследники обязаны его реализовать.
3. Убедись, что `new Pokemon(...)` **не компилируется**. Закомментируй эту строку и оставь комментарий, что так нельзя.
4. В `Main` создай **массив** (или `List<Pokemon>`) из минимум 4 разных покемонов.
5. Пройди циклом `foreach` по массиву и вызови `Attack()` и `ShowInfo()` у каждого. Обрати внимание: переменная цикла имеет тип `Pokemon`, а поведение — разное.
6. Добавь **счётчик боёв** через `static` свойство в базовом классе и увеличивай его при каждой атаке.

### Требуемый формат вывода:
```
=== ТУРНИР: ВСЕ ПРОТИВ ВСЕХ ===
Всего покемонов: 4

--- Раунд 1 ---
Пикачу (Ур. 5): Пика-пика! Удар током!
Сквиртл (Ур. 7): Сквирт-сквирт! Водяной пистолет!
Чармандер (Ур. 6): Чар-чар! Огненный хвост!
Бульбазавр (Ур. 4): Бульба! Листовой удар!

Всего атак проведено: 4
```

**Свобода:** можешь сделать раунды случайными, добавить победителя турнира, считать суммарный урон. Можешь вместо массива использовать `List<Pokemon>` и добавлять покемонов в цикле. Абстрактный класс и полиморфный вызов — обязательны.

## Задание 3. Интерфейсы: кто что умеет

**Формулировка задачи:** Добавить интерфейсы, чтобы разные покемоны умели разные вещи, не ломая иерархию наследования.

### Техническое задание:
1. Создай **минимум 2 интерфейса**:
   - `IEvolvable` с методом `void Evolve();`
   - `IFlyable` с методом `void Fly();` (или `ISwimmable`, `ITrainable` — на твой вкус).
2. Реализуй интерфейсы у подходящих наследников:
   - например, `Charmander : Pokemon, IEvolvable`;
   - `Pidgeotto : Pokemon, IFlyable, IEvolvable`;
   - `Magikarp : Pokemon` (не умеет ни то, ни другое — и это нормально).
3. В `Main`:
   - создай список/массив покемонов;
   - пройди циклом;
   - если покемон реализует `IEvolvable` — вызови `Evolve()`;
   - если `IFlyable` — вызови `Fly()`;
   - используй проверку `if (pokemon is IEvolvable evolvable) { evolvable.Evolve(); }`.
4. Выведи итог: сколько покемонов умеют эволюционировать, сколько — летать.

### Требуемый формат вывода:
```
=== СПОСОБНОСТИ ПОКЕМОНОВ ===

Чармандер (Ур. 6) умеет: атаковать, эволюционировать
Пиджеотто (Ур. 9) умеет: атаковать, летать, эволюционировать
Магикарп (Ур. 3) умеет: только атаковать (пока что...)

--- Проверка способностей ---
Чармандер эволюционирует!
Пиджеотто взлетает!
Пиджеотто эволюционирует!
Магикарп ничего не умеет, кроме Splash.

Итого:
Эволюционируют: 2
Летают: 1
```

**Свобода:** можешь добавить третий интерфейс, сделать так, чтобы эволюция меняла имя и уровень покемона, добавить проверку `as` вместо `is`. Главное — минимум 2 интерфейса и полиморфная проверка через `is`.
