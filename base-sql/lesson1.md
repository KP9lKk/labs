### Лабораторная работа №1: Проектирование ER-диаграммы базы данных «Pokémon TCG» в dbdiagram.io

#### 1. Входные данные (Контекст)

Каждая пара студентов использует ранее проанализированную карточку Покемона. Ваша задача — спроектировать визуальную реляционную ER-диаграмму на языке **DBML** в сервисе [dbdiagram.io](https://dbdiagram.io).

База данных должна корректно хранить параметры карточки, учитывать авторство, сеты, а также масштабироваться под сложные правила TCG (несколько атак на карте и комбинированную стоимость энергии).

---

#### 2. Требования к стандарту именования (Code Style)

Применяется индустриальный стандарт **Table-Prefixed Naming** в формате `snake_case`:

* **Сущности (Таблицы):** Имена сущностей строго в **единственном числе** на английском языке (`card`, `illustrator`, `attack`, `element_type`).
* **Атрибуты (Столбцы):** Каждое поле обязано содержать **префикс имени своей сущности** (`card_name`, `illustrator_name`, `attack_base_damage`, `element_type_name`).
* **Первичные ключи (PK):** Строятся строго по шаблону `<имя_таблицы>_id` (`card_id`, `illustrator_id`, `attack_id`).
* **Внешние ключи (FK):** Название внешнего ключа в дочерней таблице должно строго совпадать с именем первичного ключа родительской таблицы.

---

#### 3. Требования к архитектуре и связям

Схема должна быть описана на DBML и включать в себя следующие связи:

* **Связи 1:M (Один-ко-Многим):**
  * `illustrator` --> `card` (Один художник создает много карт).
  * `card_set` --> `card` (Один сет содержит много карт).
* **Связь M:N (Многие-ко-Многим):**
  * `card` <--> `attack` через связующую таблицу `card_attack`.
* **Связь M:N с атрибутом связи:**
  * `attack` <--> `element_type` через связующую таблицу `attack_energy_cost` с обязательным атрибутом количества требуемой энергии (`energy_quantity`).

---

#### 4. Шаблон и пример синтаксиса DBML

Работа выполняется в редакторе **dbdiagram.io**. Студенты самостоятельно определяют полный набор полей, типы данных (`int`, `text`, `numeric`, `date`) и ограничения (`pk`, `not null`, `unique`, `default`, `check:` \`card_hp > 0\`).

**Пример синтаксиса для оформления работы:**

```dbml
// Пример объявления сущности
Table illustrator {
  illustrator_id int [pk]
  illustrator_name text [not null]
}

// Пример объявления связующей таблицы
Table card_attack {
  card_attack_id int [pk]
  card_id int [not null]
  attack_id int [not null]
}

// Пример объявления связей (FK > PK)
Ref: card.illustrator_id > illustrator.illustrator_id
Ref: card_attack.card_id > card.card_id

```

#### 5. Чек-лист самопроверки перед сдачей

* [ ] В ячейках таблиц отсутствуют списки или массивы значений (данные атомарны)?
* [ ] Связь между `card` и `attack` реализована через промежуточную таблицу `card_attack`?
* [ ] Комбинированная стоимость атак вынесена в связующую таблицу `attack_energy_cost` с полем `energy_quantity`?
* [ ] Все связи `Ref:` явно заданы и ссылаются на существующие первичные ключи `PK`?
