### Лабораторная работа №2: Реализация базы данных «Pokémon TCG» в SQL DDL и рефакторинг под типы карт

#### 1. Входные данные (Контекст)

Каждая пара студентов использует ER-диаграмму, спроектированную в Лабораторной работе №1. Задача — перевести модель в рабочий SQL DDL-скрипт (`schema.sql`) для PostgreSQL, а также **провести рефакторинг схемы** для поддержки 3 типов карт TCG: Покемоны (`Pokemon`), Энергии (`Energy`) и Тренеры (`Trainer`).

---

#### 2. Требования к стандарту именования (Code Style) и PostgreSQL DDL

* **Сущности (Таблицы):** Имена строго в **единственном числе** на английском языке в нижнем регистре (`card`, `illustrator`, `attack`, `element_type`).
* **Атрибуты (Столбцы):** Обязательный **префикс имени своей таблицы** (`card_name`, `illustrator_name`, `attack_base_damage`, `energy_quantity`).
* **Первичные ключи (PK):** Строго по шаблону `<имя_таблицы>_id` с синтаксисом `INT GENERATED ALWAYS AS IDENTITY`.
* **Внешние ключи (FK):** Название `FK` в дочерней таблице должно строго совпадать с именем `PK` в родительской таблице.

---

#### 3. Техническая справка по PostgreSQL (Типы данных и DDL-конструкции)

##### Выбор базовых типов данных

* **`INT`** — Целые числа (HP, количество карт, уроны).
* **`NUMERIC(p, s)`** — Точные дробные числа для физических величин (рост, вес). *Пример:* `NUMERIC(5, 2)` поддерживает значения до `999.99`.
* **`TEXT`** — Любые строковые текстовые данные произвольной длины (имена, эффекты, коды сетов). В PostgreSQL `TEXT` так же эффективен, как `VARCHAR(n)`, но исключает искусственные лимиты длины.
* **`DATE`** — Календарные даты в формате `YYYY-MM-DD`.

##### Справочник синтаксиса ограничений (Constraints)

```sql
-- 1. Первичный ключ с автоинкрементом по стандарту SQL:2003
card_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- 2. Запрет на NULL-значения и проверка уникальности
set_code TEXT NOT NULL UNIQUE

-- 3. Проверки значений (CHECK Constraints)
card_hp INT CHECK (card_hp > 0)
card_weight_kg NUMERIC(5, 2) CHECK (card_weight_kg > 0)

-- 4. Внешний ключ (Foreign Key)
illustrator_id INT REFERENCES illustrator(illustrator_id)

-- 5. Составной первичный ключ для связующих таблиц
PRIMARY KEY (card_id, attack_id)

```

#### 4. Задание на рефакторинг: Архитектура типов карт

В TCG существует 3 принципиально разных вида карт с разным набором атрибутов:

1. **Покемон (`Pokemon`):** Имеет HP, рост, вес, стадию эволюции, привязку к атакам и типу стихии.
2. **Энергия (`Energy`):** Не имеет HP или атак, предоставляет определенный тип стихии (`element_type_id`) и может быть базовой/специальной (`is_special`).
3. **Тренер (`Trainer`):** Не имеет HP, имеет подтип (`Item`, `Supporter`, `Stadium`) и текстовый эффект применения.

**Задача студентов:**
Продумать и реализовать единую общую таблицу `card` (базовые атрибуты: имя, сет, художник, год) и спроектировать корректную связь с дочерними специфичными таблицами или атрибутами типезации карт без дублирования `NULL`-полей.

---

#### 5. Пример базовой структуры DDL-скрипта (`schema.sql`)

```sql
-- 1. Справочники (создаются первыми)
CREATE TABLE illustrator (
    illustrator_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    illustrator_name TEXT NOT NULL
);

CREATE TABLE element_type (
    element_type_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    element_type_name TEXT NOT NULL UNIQUE
);

-- 2. Главная сущность карт
CREATE TABLE card (
    card_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    card_name TEXT NOT NULL,
    card_type TEXT NOT NULL CHECK (card_type IN ('pokemon', 'energy', 'trainer')),
    illustrator_id INT REFERENCES illustrator(illustrator_id)
);

-- 3. Дочерние таблицы и связи (создаются в конце)
CREATE TABLE card_pokemon (
    card_id INT PRIMARY KEY REFERENCES card(card_id),
    pokemon_hp INT NOT NULL CHECK (pokemon_hp > 0),
    pokemon_weight_kg NUMERIC(5, 2) CHECK (pokemon_weight_kg > 0),
    element_type_id INT NOT NULL REFERENCES element_type(element_type_id)
);

```
