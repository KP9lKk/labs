# Лабораторная работа № 1
## Тема: Первый REST API на C#. Minimal API в Rider, Swagger и HTTP Client

## 1. Краткие теоретические сведения

### 1.1. Что такое API и зачем он нужен

API (Application Programming Interface) — это **контракт** между двумя программами. Одна программа (клиент) говорит: «дай мне вот это», другая (сервер) отвечает: «держи, вот твой JSON». Клиент не лезет внутрь сервера, не знает, где там база данных и как она устроена. Ему важен только контракт.

Аналогия: **API — это официант в ресторане**. Ты (клиент) не заходишь на кухню и не готовишь сам. Ты говоришь официанту: «Принеси пасту карбонара». Официант идёт на кухню (сервер), возвращается и приносит результат. Если пасты нет — возвращается с сообщением «нет такого блюда». Всё общение — по понятным правилам.

Правила этого общения в вебе называются **HTTP** и **REST**.

### 1.2. HTTP-методы: язык API

Каждый запрос к API содержит **метод** — глагол, который говорит, что мы хотим сделать.

| Метод | Что делает | Пример |
|-------|------------|--------|
| `GET` | Получить данные | Список покемонов, один покемон по id |
| `POST` | Создать новый ресурс | Добавить покемона в покедекс |
| `PUT` | Полностью заменить ресурс | Перезаписать покемона по id |
| `PATCH` | Частично обновить | Изменить только уровень |
| `DELETE` | Удалить | Убрать покемона из покедекса |

Важно: **метод — это часть контракта**. Если ты хочешь что-то создать — это всегда `POST`, а не `GET`. Даже если очень хочется.

### 1.3. Коды ответов: что сервер говорит клиенту

Каждый ответ содержит **код** — короткое число, которое говорит, всё ли прошло хорошо.

- **2xx — успех:**
    - `200 OK` — всё хорошо, вот данные.
    - `201 Created` — новый ресурс создан (обычно после `POST`).
    - `204 No Content` — всё ок, но возвращать нечего (например, после `DELETE`).
- **4xx — ошибка клиента:**
    - `400 Bad Request` — ты прислал что-то не то (невалидные данные).
    - `401 Unauthorized` — ты не авторизован.
    - `403 Forbidden` — ты авторизован, но тебе нельзя.
    - `404 Not Found` — такого ресурса нет.
- **5xx — ошибка сервера:**
    - `500 Internal Server Error` — что-то упало у нас, не у тебя.

**Правило:** клиент виноват — `4xx`, сервер виноват — `5xx`. Если ты не уверен, чей код использовать — почти всегда это `400` или `404`.

### 1.4. Инструменты для работы с API

Чтобы отправлять HTTP-запросы и смотреть ответы, нужен специальный инструмент. Самый известный — **Postman**, но он требует регистрации для работы с коллекциями (сохранение запросов в группы). Есть бесплатные аналоги **без регистрации**.

**Bruno** — открытый, лёгкий, работает офлайн. Не требует аккаунта, хранит коллекции как обычные файлы в папке, умеет экспортировать в формат Postman. Идеально для учёбы и работы в команде через Git.

Мы будем использовать **Bruno** для части 1 (публичные API) и **Rider HTTP Client** для части 2 (свой API). Это даёт полный цикл без регистраций и лишних установок.

### 1.5. Minimal API: минимум кода — максимум дела

В ASP.NET Core есть два подхода: **контроллеры** и **Minimal API**. Контроллеры — это классика, но для старта они громоздкие. Minimal API — это буквально несколько строк на всё.

```csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/hello", () => "Привет, мир API!");

app.Run();
```

Три строки — и у тебя работает HTTP-сервер. Запустил — перешёл в браузер или HTTP Client — увидел ответ.

### 1.6. Swagger: документация, которая всегда актуальна

**Swagger** (он же OpenAPI) — это автоматически генерируемая документация твоего API. ASP.NET Core умеет строить её прямо из кода: если у тебя есть эндпоинт `GET /pokemons/{id}`, Swagger сам покажет его в браузере, опишет параметры и даст кнопку «Try it out».

Плюсы:
- не надо писать README вручную;
- клиенты (фронтенд, мобилка, коллеги) сразу видят контракт;
- можно дёргать эндпоинты прямо из браузера, без сторонних программ;
- если ты изменил код — Swagger обновится сам.

В шаблоне `dotnet new webapi` Swagger уже подключён. Всё, что нужно — открыть `http://localhost:5000/swagger` (порт может отличаться).

### 1.7. Rider: IDE

**Работа в Rider строится так:**
1. `File → New Solution → ASP.NET Core Web Application` — создаём проект.
2. Указываем тип **Minimal API**.
3. Нажимаем зелёный треугольник — проект собирается и запускается.
4. Открываем Swagger в браузере, либо шлём запросы из `.http`-файла внутри IDE.
5. Ставим точки останова и дебажим.

### 1.8. CRUD и HTTP

CRUD — это четыре базовые операции над данными: Create, Read, Update, Delete. В REST они ложатся на HTTP-методы так:

| CRUD | HTTP | Пример маршрута | Типичный код ответа |
|------|------|-----------------|---------------------|
| **C**reate | POST | `/pokemons` | 201 Created |
| **R**ead (все) | GET | `/pokemons` | 200 OK |
| **R**ead (одно) | GET | `/pokemons/{id}` | 200 OK или 404 |
| **U**pdate | PUT | `/pokemons/{id}` | 200 OK или 204 |
| **D**elete | DELETE | `/pokemons/{id}` | 204 или 404 |

Запомни это как таблицу умножения — она всплывёт на каждом собеседовании.

### 1.9. Частая ошибка новичка

Использовать `GET` для всего. «Хочу удалить — сделаю `GET /deletePokemon?id=1`». Так делать **нельзя**. Метод — это часть контракта, и клиенты (браузеры, HTTP Client, чужие программы) ожидают, что `GET` — безопасный и не меняет данные, а `DELETE` — меняет. Если нарушаешь правило, ломаются кэши, браузеры, прокси и весь веб.

Второй частый промах — возвращать `200 OK` на любую ошибку с текстом «not found» в теле. Так нельзя: код ответа — это часть контракта. Не нашёл — `404`. Невалидные данные — `400`. Сервер упал — `500`.

### 1.10. Как выбрать код ответа за 5 секунд

1. **Всё прошло, данные есть?** → `200 OK`.
2. **Создал что-то новое?** → `201 Created` + заголовок `Location`.
3. **Удалил, возвращать нечего?** → `204 No Content`.
4. **Не нашёл ресурс?** → `404 Not Found`.
5. **Клиент прислал мусор?** → `400 Bad Request`.
6. **Что-то сломалось у меня?** → `500 Internal Server Error`.

## Часть 1. Bruno и публичные API

**Формулировка задачи:** научиться отправлять HTTP-запросы через Bruno, читать ответы, понимать коды, сохранять запросы в коллекцию.

### Техническое задание:

1. **Установи Bruno** (https://www.usebruno.com/downloads). Регистрация не требуется — Bruno работает полностью офлайн.

2. Создай новую **коллекцию** с названием `Lab1 — Public API`. Bruno создаст папку на диске, где будут храниться все запросы как обычные файлы.

3. Выполни **пять запросов** и сохрани их в коллекцию:

   **3.1. Факт о коте** (GET):
   ```
   GET https://catfact.ninja/fact
   ```
   Ожидаемый код: `200 OK`. Тело: JSON с полем `fact`.

   **3.2. Случайный пользователь** (GET):
   ```
   GET https://randomuser.me/api/
   ```
   Ожидаемый код: `200 OK`. Тело: JSON с массивом пользователей.

   **3.3. Один пост** (GET):
   ```
   GET https://jsonplaceholder.typicode.com/posts/1
   ```
   Ожидаемый код: `200 OK`. Тело: JSON с постом.

   **3.4. Создать пост** (POST):
   ```
   POST https://jsonplaceholder.typicode.com/posts
   Content-Type: application/json

   {
     "title": "Мой первый покемон",
     "body": "Поймал Пикачу!",
     "userId": 1
   }
   ```
   Ожидаемый код: `201 Created`. Обрати внимание на заголовок `Location` в ответе — там адрес нового ресурса.

   **3.5. Сломанный запрос** (GET):
   ```
   GET https://jsonplaceholder.typicode.com/postsss
   ```
   Ожидаемый код: `404 Not Found`. Это учебная ошибка — так ты увидишь, как выглядит «ресурса нет».

4. Для **каждого** запроса в коллекции:
    - дай осмысленное имя (например, «Факт о коте», «Создать пост»);
    - в описании напиши, что делает запрос и какой код ожидается.

5. Дополнительно (бонус к оценке): сделай запрос с **query-параметром**:
   ```
   GET https://catfact.ninja/facts?limit=3
   ```
   Сохрани его тоже. Обрати внимание: тот же эндпоинт, но другой URL — другой результат.

6. **Экспортируй коллекцию**: правой кнопкой на коллекцию → `Export` → формат `Bruno Collection` (или `Postman Collection`). Сохрани файл как `public-api.bruno.json` или `public-api.postman_collection.json`.

### Требуемый результат:

Файл с экспортированной коллекцией, содержащий **шесть** запросов (5 обязательных + 1 бонусный). Каждый запрос имеет имя, описание и сохранён в правильной папке (например, `Cats`, `Users`, `Posts`).

**Свобода:** можешь заменить публичные API на свои (например, открытые API курсов валют, погоды, GitHub). Можешь использовать Hoppscotch вместо Bruno — результат тот же, коллекция экспортируется в JSON. Главное — минимум 5 запросов, минимум 1 `POST`, минимум 1 запрос с «ошибочным» кодом.

## Часть 2. Minimal API в Rider

**Формулировка задачи:** написать свой Minimal API для покедекса (коллекции покемонов), подключить Swagger, проверить все эндпоинты через Swagger и HTTP Client в Rider.

Хранилище — **в памяти** (`List<Pokemon>`). Базу данных подключим в следующих лабораторных.

### Шаг 1. Создание проекта в Rider

1. `File → New Solution…`
2. Выбери тип проекта **ASP.NET Core Web Application**.
3. Укажи:
    - **Name:** `PokedexApi`
    - **Solution name:** `PokedexApi`
    - **Framework:** .NET 8 (LTS)
    - **Type:** **Minimal API**
    - **Enable OpenAPI (Swagger):** ✅
    - **Use HTTPS:** ✅
4. `Create`. Rider подтянет зависимости и покажет `Program.cs`.

### Шаг 2. Запуск и проверка Swagger

1. Нажми **зелёный треугольник** рядом с методом `Main` — проект соберётся и запустится.
2. В окне `Run` Rider увидишь:
   ```
   Now listening on: http://localhost:5000
   Now listening on: https://localhost:5001
   ```
   (порт может отличаться — смотри в выводе).
3. Открой в браузере `https://localhost:5001/swagger` — увидишь автогенерированную документацию API. Пока там только тестовый эндпоинт из шаблона.

### Шаг 3. Задание 2.1. Модель и первые эндпоинты

1. В `Program.cs` **до** строки `var builder = ...` объяви модель:

```csharp
public record Pokemon(int Id, string Name, string Type, int Level);
```

2. После `var app = builder.Build();` и до `app.Run();` создай список покемонов:

```csharp
var pokemons = new List<Pokemon>
{
    new(1, "Pikachu", "Electric", 12),
    new(2, "Charmander", "Fire", 8),
    new(3, "Squirtle", "Water", 10)
};
```

3. Реализуй три эндпоинта:
    - `GET /hello` — возвращает строку `"Привет, мир API!"`.
    - `GET /pokemons` — возвращает список всех покемонов.
    - `GET /pokemons/{id}` — возвращает одного покемона по id или `404`, если его нет.

4. Перезапусти проект. Обнови Swagger — новые эндпоинты появятся там автоматически. Дёрни каждый эндпоинт прямо из Swagger (кнопка **Try it out → Execute**).

### Шаг 4. Задание 2.2. Полный CRUD

Добавь к существующим эндпоинтам ещё три:

- `POST /pokemons` — добавить нового покемона в покедекс. Возвращать `201 Created` с заголовком `Location: /pokemons/{id}`.
- `PUT /pokemons/{id}` — заменить покемона по id. `404`, если нет; `200` с обновлённым объектом, если есть.
- `DELETE /pokemons/{id}` — удалить покемона по id. `404`, если нет; `204 No Content`, если есть.

**Важно:** при `POST` id генерируется автоматически (`max(id) + 1`). Клиент его не присылает.

После реализации перезапусти проект и проверь **каждый** метод в Swagger. Обрати внимание на коды ответов — они должны соответствовать таблице из п. 1.8.

### Шаг 5. Задание 2.3. Валидация

Реализуй валидацию входящих данных для `POST` и `PUT`:

- `Name` — не пустой и не короче 2 символов;
- `Level` — в диапазоне от 1 до 100;
- `Type` — из списка разрешённых (`Fire`, `Water`, `Grass`, `Electric`, `Psychic`, `Normal`, `Flying`, `Poison`).

Если данные невалидны — верни `400 Bad Request` с описанием ошибок:

```json
{
  "errors": [
    "Name должен быть не короче 2 символов",
    "Type 'Rock' не поддерживается",
    "Level должен быть в диапазоне 1..100"
  ]
}
```

Проверь в Swagger: `POST` с мусором не должен добавлять покемона.

### Шаг 6. Тестирование через HTTP Client в Rider

Rider умеет отправлять HTTP-запросы без сторонних программ — через `.http`-файлы. Это встроенная возможность IDE, ничего дополнительно устанавливать не нужно.

1. Создай в корне проекта файл `requests.http`.

2. Напиши в нём **шесть запросов**, повторяющих твои эндпоинты:

```
@baseUrl = https://localhost:5001

### Получить всех покемонов
GET {{baseUrl}}/pokemons

### Получить одного покемона
GET {{baseUrl}}/pokemons/1

### Получить несуществующего покемона (ожидаем 404)
GET {{baseUrl}}/pokemons/999

### Добавить покемона
POST {{baseUrl}}/pokemons
Content-Type: application/json

{
  "name": "Bulbasaur",
  "type": "Grass",
  "level": 6
}

### Обновить покемона
PUT {{baseUrl}}/pokemons/2
Content-Type: application/json

{
  "name": "Charmeleon",
  "type": "Fire",
  "level": 16
}

### Удалить покемона
DELETE {{baseUrl}}/pokemons/3

### Добавить покемона с невалидными данными (ожидаем 400)
POST {{baseUrl}}/pokemons
Content-Type: application/json

{
  "name": "X",
  "type": "Rock",
  "level": 999
}
```

3. Рядом с каждым запросом появится **зелёная стрелка** — нажми, и Rider отправит запрос прямо из IDE. Результат откроется в панели `Services` или во вкладке `Run`.

4. **Обрати внимание на коды ответов** в правой части окна. Они должны совпадать с ожидаемыми.

5. Если хочешь, добавь переменные окружения в `.http`-файл (например, `@host` и `@token`), чтобы менять адрес одной строкой.

### Шаг 7 (бонус к оценке). Импорт коллекции из Bruno

Rider умеет импортировать коллекции Postman и конвертировать их в `.http`-файлы. Если ты делал часть 1 в Bruno и экспортировал коллекцию в формате Postman, попробуй:

1. Экспортируй коллекцию Bruno в формате `Postman Collection`.
2. В Rider: `Ctrl+Shift+A` → начни вводить `Import from Postman Collection File` → выбери файл.
3. Rider создаст `.http`-файл с твоими запросами. Сравни его с тем, что ты написал вручную.

Это покажет, как инструменты работают вместе.

Работа сдаётся в двух частях. Проект должен компилироваться без ошибок и запускаться через Rider. Все эндпоинты должны быть проверены в Swagger и `.http`-файле. Работа оценивается по 3-балльной шкале.

**Вопросы к защите (чтобы не было скучно):**

1. Чем `POST` отличается от `PUT`? Когда использовать что?
2. Зачем нужен код `201 Created`, если клиент и так видит, что всё сработало?
3. Почему `DELETE` обычно возвращает `204`, а не `200` с телом?
4. Что произойдёт, если клиент отправит `POST /pokemons` с полем `id` в теле? Это ошибка или нет?

6. Чем path-параметр отличается от query-параметра? Приведи пример, где нужен каждый (например, фильтр по типу покемона).
7. Что такое Swagger? Зачем он нужен, если есть `.http`-файл? А наоборот — зачем `.http`-файл, если есть Swagger?

9. Чем работа с API в Rider через `.http`-файл отличается от Bruno? Когда что удобнее?
10. **Если клиент прислал невалидные данные, какой код ответа ты вернёшь и почему именно его? А если сервер не смог подключиться к базе — какой код? Почему разница?**
